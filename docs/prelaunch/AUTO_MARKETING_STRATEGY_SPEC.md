# 自动化营销（发券）策略 Spec

日期：2026-08-28
状态：P0 实施中

---

## 0. 背景

- 目标用户：县城 / 小城的夫妻店餐馆，不懂营销、没精力配置。
- 产品诉求：**商家不用计算**，且满足三条：
  1. **不会亏钱**
  2. **让消费者觉得占便宜**
  3. **数据越多，发券效果越好**（自适应，最终形成算法推券）
- 现状问题（本次触发）：
  - 建店种子 `DEFAULT_COUPON_RULES` 和平台动态 `build_dynamic_rules` 两套规则打架，`locked` 兼容层让写死的 ¥5满18 / 1天过期 / 券名"超过80%用户"发给了顾客。
  - **已修**（commit 44c4511）：只保留 `build_dynamic_rules` 一套，种子瘦成 `{enabled}` 开关，读写路径统一 `normalize_coupon_rules`。
- 本 Spec 在"只有一套规则"的基础上，把这一套做对、做到自适应。

## 1. 保留的这一套是什么

`app/core/platform_rules.py::build_dynamic_rules(aov, intensity)`：
- 输入：商户近 30 天平均客单价 AOV + 商户选的营销强度（保守 / 标准 / 激进）。
- 输出：5 个发券时机的规则（进店券 / 新客券 / 复购券 / 老客召回券 / 积分好礼券），每个带面额 / 门槛 / 有效期 / 加权组合。
- 商户侧只暴露：营销强度旋钮。券的经济性参数不暴露、不可配。

## 2. 已发现的缺陷（要在 P0 修）

| # | 缺陷 | 影响 |
|---|---|---|
| A | **AOV 用实付价算**（`avg(Order.total)`，`Order.total = 原价 − 优惠券折扣`） | 发券 → 用券 → 实付降 → AOV 降 → 券越算越小，向下螺旋 |
| B | **冷启动兜底写死 30 元**（`aov < 10 → aov = 30`） | 面馆客单 12，兜底 30 算出的满减券用不上 |
| C | **所有业态都发"满X减Y"** | 对一碗面（就点一份）满减是废券 |
| D | **新客券有效期只有 3 天** | 新客券的意义是"给下次来的理由"，3 天太短 |
| ~~E~~ | ~~没有毛利率约束~~ —— **不做**：毛利数据靠商家手填、不可靠；卡券只会压小体感。改用 F 的总闸从总账兜。 | — |
| F | **没有优惠预算总闸** | 极端情况下近30天优惠总额可能吃掉过多毛利 —— **已修**（P0-6） |
| G | **商家看不到成本** | 商家不知道自己在发券 / 发了多少 / 花了多少 / ROI |

## 3. 核心框架：客单价带 × 数据自适应

不再用一条线性公式 `aov × 系数`，改为按**客单价带**决定券形态。
「不亏钱」不靠拍毛利率去卡单张券（毛利数据不可靠、且会把券压小到没体感），
而是靠**月优惠预算总闸**（近 30 天优惠总额 ≤ GMV × X%）。

### 3.1 进店券 = 开盲盒（① 加料框架 + ② 力度分层 + ③ 门槛收窄）

进店券每次扫码都发、当日有效、量最大，是最容易把钱撒没、战略价值又最低的一条线
（它常常在补贴"本来就会发生的订单"）。所以它的设计目标是：**平均花费低、峰值体感强**——
做成开盲盒，绝大多数抽到小券，少数抽到"手气爆棚"。

| 档 | 权重 | 门槛 | 面额 | 消费者感受 |
|---|---|---|---|---|
| 开胃小券 | 60 | 客单价 ×0.9（**已经达标**） | 门槛 ×8% | 一张干净的小折扣，没有"多花才省"的别扭 |
| 加菜小券 | 28 | 客单价 ×1.15（多一道菜） | ≈ 门槛与客单价的**差额**（门槛 ×14%） | "加的那道菜白送" → 客单价被往上带 |
| 手气爆棚 | 12 | 客单价 ×1.0（正常吃就到） | 贴近结算红线（门槛 ×18%，`_jackpot_amount`） | 18% 的大券，肉眼可见地大 |

micro 带（客单价 ≤ 20，面馆快餐单品店多）：开胃小券/手气爆棚两档改**无门槛立减**
（`threshold = 0`）保证单品店也能用掉，只保留"加菜小券"一档带低门槛。

**③ 旧 bug 修复**：进店券/复购券最高档门槛以前是 `客单价 ×1.6` / `×1.4`——火锅
客单价 90，算出"满 144 减 12"，消费者的心理账是"多花 54 省 12"，负体感。现在
所有档门槛收进 `0.9 ~ 1.25 × 客单价`。

### 3.1b 其余券的力度（也按 ② 分层 / 给够）

| 券 | 调整 |
|---|---|
| 复购券 | 三档 55/30/15，最高档用 `_jackpot_amount`（"下次来省一道菜"）；门槛收进 0.9~1.25×AOV |
| 新客券 | 面额 7% → **12%**（micro 无门槛 18%），21 天有效——这是"给下次来的理由"，要给够 |
| 老客召回券 | 门槛压到 0.7×AOV（好用掉）+ 面额直接给 `_jackpot_amount`（~18%）——最该舍得的一张 |
| `_jackpot_amount(门槛, 强度乘数)` | = `门槛 × min(18%×乘数, 19%)`，绕开 `SAFE_INTENSITY_CEILING` 15% 软上限（那条上限是给"每单都发"的常规档留缓冲的），单笔仍被结算红线 20% 兜底 |

> 三档强度（保守/标准/激进）现在肉眼可分：火锅进店券加权期望值 保守 ≈7.9 / 标准 ≈9.4 / 激进 ≈10.5 元。

### 3.2 冷启动客单价：从菜单算，业态只兜底兜底

单量 < `AOV_MIN_ORDERS`(5) 时，客单价按优先级取：

1. **菜单菜品价格中位数 × 1.2**（`coupon_service._menu_price_estimate`）——人均点一份多一点，商家录菜单时系统已经知道，不用问业态。
2. 连菜单都没有 → `INDUSTRY_PRESETS[industry].fallback_aov`（`business_info.industry`，商家可选；未选=default=40）。这张表**不再带毛利率**。

| industry key | 名称 | 兜底兜底客单价(元) |
|---|---|---|
| `noodle` | 面馆/粉店 | 14 |
| `fastfood` | 快餐/盖饭/简餐 | 18 |
| `breakfast` | 早餐 | 10 |
| `drink` | 饮品/奶茶 | 15 |
| `stirfry` | 小炒/家常菜 | 45 |
| `hotpot` | 火锅/麻辣烫 | 90 |
| `bbq` | 烧烤 | 80 |
| `dinner` | 正餐/中餐厅 | 110 |
| `default` | 未选 | 40 |

### 3.3 不亏钱：两道单券红线 + 一个总闸

1. **结算红线**（已有 `cap_discount_amount`）：单券实际减免 ≤ 本单实付 × 20%。
2. **模板红线**（已有 `assert_template_economics_safe`）：面额 ≤ 门槛 × 20%（无门槛立减靠结算红线兜）。
3. **月优惠预算总闸**（P0-6）：`近 30 天优惠总额 ≤ 近 30 天 GMV(原价口径) × X%`（保守 3% / 标准 5% / 激进 8%）。超过 → `issue_auto_coupon` / `issue_entry_coupon` 直接不发，reason=`本月优惠预算已用尽`。
   - 滚动 30 天窗口，自然重置，避免「月初预算全空→全部拦截」。
   - 冷启动不设限：`订单数 < 10` 或 `GMV < 300` 放行，先把量做起来。
   - 比例从 2/4/7 上调到 3/5/8：券改成盲盒后单张体感强了、平均花费略升，标准档留 5% 才不至于活跃商家天天撞闸。

> ~~毛利率红线~~ —— **P0 审计后撤销**。毛利数据不可靠，且它把券压小到没「占便宜」体感，与核心诉求相反。不亏钱交给上面的总闸。

### 3.4 有效期

| 券 | 有效期 |
|---|---|
| 进店券 | 当日 (`valid_days = 1`) |
| 新客券 | **21 天**（P0 从 3 改） |
| 复购券 | 7-15 天 |
| 老客召回券 | 7 天 |
| 积分好礼券 | 30 天 |

## 4. 数据越多越准：三阶段演进

| 阶段 | 数据量 | 策略来源 | 何时做 |
|---|---|---|---|
| **阶段 0 冷启动** | 0-5 单 | 菜单估价（菜品价中位数 ×1.2）→ 业态 fallback_aov 兜底（3.2）：定客单价带 + 券形态 | P0 |
| **阶段 1** | 5-50 单 | 真实客单价（**原价口径、取中位数**防大单拉偏）替换估价；券形态仍按客单价带 | P0（原价）+ P1（中位数、分时段） |
| **阶段 2 算法推券** | 50+ 单 | **核销率 + 复购率闭环调参**：某档核销率 <10% → 门槛太高 / 力度太小，自动下调；核销率 >60% 但复购未提升 → 力度过剩，收一点。叠加：分时段、分新老客、流失预警加码、A/B 迭代基线 | P1 / P2 |
| **阶段 3 跨店** | 平台有 N 家同业态店 | 新店冷启动直接用"同城同业态"的成熟参数，而不是通用兜底 | P2 |

> 阶段 2 的"算法"不上深度学习：`核销率 / 复购率 / 客单价 / 时段 / 周几` 喂进规则树或梯度提升即可，可解释、可回滚。

## 5. 商家侧只碰 3 样东西

1. **业态**：开店选一次（`business_info.industry`），可改。
2. **营销强度**：保守 / 标准 / 激进 旋钮（`business_info.marketing_intensity`，已有）。
3. **一屏经营看板**（P0 补齐）：
   - 本月发出 X 张 / 核销 Y 张 / 核销率
   - 本月优惠总额 Z 元 / 预算进度条（Z / GMV×X%）
   - 券带来的复购单数 N / 粗略 ROI
   - 一句话建议（"核销率偏低，可切到激进档" / "预算即将用尽，本月自动降频"）

## 7. 验收（每次改动都要）

- **端到端**：建店（选业态）→ 扫码入会 → 打开菜单 → 首单支付，逐张检查实际发出的券：面额 / 门槛 / 有效期 / 券名，与本 Spec 对得上。
- **券质量监控**（P0.5 一并加）：每周统计「有效期 < 7 天的新客券占比」「券名非白名单占比」「单券名义力度 > 20% 占比」，非零即告警。
- **不亏验证**：造一批不同客单价的样例订单，跑发券 + 结算，确认没有一单减免超过实付 20%、且近30天累计优惠不超预算总闸。
