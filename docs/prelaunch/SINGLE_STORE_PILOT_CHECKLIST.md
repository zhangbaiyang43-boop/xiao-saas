# 单店 PRINT_FIRST 试点前检查清单

适用：给一家**真实门店**开启 PRINT_FIRST（"普通订单安静，只有异常才响"）之前，逐项勾选。
一家店一份。每个 `[ ]` 都要有证据（输出 / 截图 / 记录），没有证据按"没做"算。

状态约定：`[x]` 已验证；`[ ]` 未做；`[~]` 部分完成。
不要在这份清单、聊天记录或截图里出现 appId、appSecret、sn、密钥、手机号。只写"已配置 / 未配置"。

背景：

- 默认模式 `WORKBENCH`（老板在手机上点"开始"、"完成"）。`PRINT_FIRST` 下系统自动出小票，普通订单不需要任何人点击。
- 模式存在 `TenantConfig.business_info["fulfilment_mode"]`，**按店设置，默认 WORKBENCH**。商家设置接口会拒绝写这个字段，只能由运维人员在服务器上改（见 `saas-base/app/services/fulfilment_mode.py`）。任何读不到 / 写错的值都按 WORKBENCH 处理。
- 这份清单对应的发布版本：`43f4e673`（打印恢复、打印异常短信升级、PRINT_FIRST 模式）。

---

## 1. 门店与权益

- [ ] 已确认是**哪一个**租户（核对租户名称和 id 前缀；名字相近的店很多，登错过一次）
- [ ] 订阅有效，且有效套餐为 STANDARD 或 PRO（`KITCHEN_PRINT` 能力要求）。**试用期过期会回落为 FREE，没有打印能力。** 用有效套餐查询确认，不要只看后台显示的名字
- [ ] 订阅的到期日已记下，并且晚于试点结束日
- [ ] 这家店是真实有顾客的店，不是测试账号（试点要的是真实流量下的证据）

## 2. 打印机

- [ ] 打印机型号已记录（`result` 接口只支持部分机型，见 `docs/engineering/KUAIMAI_PRINTER_INTEGRATION.md`）
- [ ] 后台打印机配置完整：服务商为快麦，`app_id` / `app_secret` / `sn` 均已配置（只记"已配置"）
- [ ] 打印机已联网，纸张充足，快麦控制台显示在线
- [ ] 后台"测试打印"成功出纸，且订单模板的内容、字体、分单符正常
- [ ] 用 `batchStatus` 只读脚本查询：在线状态 ONLINE、设备状态"正常"、等待打印数 0（脚本见快麦对接说明第 6 节）
- [ ] 已确认打印机放在**厨房里看得见、听得见的位置**，不是收银台抽屉里

## 3. 收款与下单模式

- [ ] 店铺收款模式已确认：`prepay`（先付）、`postpay`（后付）或 `table_account`（桌台挂账）
- [ ] 如果是 prepay：微信支付商户已核验（`receiver_verified`），线上收款已开通（`wx_pay_enabled`），真机走通过一次下单支付
- [ ] 如果是 postpay / table_account：收银员知道**整桌结账时要确认已收款**（PRINT_FIRST 下，未付款的待处理订单只有在结账请求里明确确认收款，才不会卡住结账）
- [ ] 桌牌 / 取餐号：确认 `pickup_no_enabled` 与 `pickup_no_required_before_print` 的设置。**开着"出票前必须有取餐号"时，没取餐号的订单会被延后出票**，如果门店不用桌牌就必须关掉

## 4. 在 WORKBENCH 模式下彩排（不改模式）

- [ ] 一整套流程走通：下单 → 出纸 → 开始 → 完成 → 整桌结账
- [ ] 出纸内容与订单一致（品项、数量、桌号、备注）
- [ ] 顾客端看到的状态文案与实际一致（不出现"商家已接单"之类系统并不知道的说法）
- [ ] 后台刷新后，订单数据、打印状态、金额都正确

## 5. 打印机离线实测（试点前必须有结论）

目的：弄清楚打印机断电 / 断网时，**系统看到什么、纸会不会补出来、要等多久才能发现**。当前已知的只有："短时断电后，订单显示出票成功，通电后纸自动出来"。其他情况没有证据。

在测试商户（没有真实顾客）上做，不要在真实门店做。

准备：

- [ ] 手机时间准确，所有时间记**北京时间**（数据库时间是 UTC，加 8 小时）
- [ ] 只关打印机，路由器和网络保持开着
- [ ] 先下一单确认秒出纸（基线），并用 `batchStatus` 脚本记录基线

做法（连续断电 180 分钟，期间分时间点下单）：

| 时间点 | 动作 | 备注栏填 |
|---|---|---|
| 0 分钟 | 打印机断电，记录断电方式 | — |
| 断电后每 5 分钟，到 30 分钟 | 运行 `batchStatus` 脚本，记录第一次变成 OFFLINE 的时间 | — |
| +1 分钟 | 下第 1 单，新桌号 | `T0` |
| +30 分钟 | 下第 2 单，新桌号 | `T30` |
| +60 分钟 | 下第 3 单，新桌号 | `T60` |
| +120 分钟 | 下第 4 单，新桌号 | `T120` |
| +179 分钟 | 下第 5 单，新桌号 | `T179` |
| +180 分钟 | 打印机通电，**不要点任何补打** | — |
| 通电后 1 分钟、5 分钟 | 运行 `batchStatus` 脚本 | — |

每次下单后：立刻看后台显示什么，立刻运行一次 `batchStatus`（看等待打印数有没有增加）。
5 分钟后如果有缺的纸，再对缺的那几单点补打，单独记录补打结果。

每一单记录：下单时间、标记、桌号、订单尾号、提交后后台显示什么、开机后是否自动出纸、出纸时间、出纸顺序、张数、内容是否正确、手动补打结果。

整体记录：断电时间、断电方式、通电时间、第一张纸出来的时间、一共出了几张、有没有重复、有没有乱序、快麦控制台上设备状态何时从在线变离线 / 再变在线。

事后只读核对（列出每一单的系统记录，和手写的"实际出纸"对照）：

- 订单号尾 4 位、桌号、订单状态、`print_status`、下单时间（北京）、`attempts`、`last_error`、手动补打次数；
- 读 `Order.print_status` 与 `merchant_note` 里 `__PRINT_META__` 之后的 JSON（`initial_print`），**只打印状态 / 次数 / 错误 / 时间**，不要输出配置。

结果解读：

| 现象 | 说明 | 对试点的影响 |
|---|---|---|
| 5 单全部在通电后自动出纸 | 云队列至少保留 3 小时 | 短时离线能自愈，但**仍然没人知道离线发生过**，仍需要告警或人工检查 |
| 较早的几单没出来，较晚的出来了 | 找到队列保留上限：没出来的最晚一单的等待时长 | 试点规则必须写明"离线超过 X 分钟，通电后要人工补打缺的单" |
| 全部没出来 | 云端不保留，或长时间离线后需要重新绑定 | 严重：离线 = 丢单，没有离线检测不能试点 |
| 某一单后台显示失败，`last_error` 含 4005 | 云端判定离线后，提交会同步失败 | 说明离线能被系统发现，记下是断电后第几分钟开始 |
| `batchStatus` 一直是 ONLINE | 心跳判断延迟很长，或该接口对这个机型无效 | 不能依赖 `batchStatus` 做告警 |
| 出现重复 / 乱序 | 云端补打有副作用 | 记入试点期间"重复出纸"的判断标准 |
| 手动补打也失败 | 补打路径不通 | 先别试点，看错误信息 |

可选的第二轮（第一轮结果合格才做）：

- [ ] 断网不断电：打印机开着，断开它的网络 30 分钟，期间下 1 单，恢复后看是否补打（真实门店断网比断电常见）
- [ ] 过夜：打烊后断电，次日早上通电，中间只留 1 单

收尾：

- [ ] 打印机恢复，下一单确认秒出纸
- [ ] 测试订单全部清理（整桌结账或拒单），不留待处理订单

结论记录（填完才算本节完成）：

- 断电后云端多久显示 OFFLINE：______
- 离线期间提交订单是否返回 4005：______
- 云队列保留多久（最长补打成功的间隔）：______
- 缺纸 / 开盖时 `deviceStatus` 与提交结果：______（可选，没测就写"未测"）

## 6. 打印异常短信升级

PRINT 异常达到阈值时，服务端会给老板的登录手机号发短信。**需要两个短信模板，审核通过之前这条链路是休眠的。**

- [ ] 告警模板已在腾讯云短信控制台提交并**审核通过**：一个数字参数 `{1}` = 受影响订单数
- [ ] 恢复模板已审核通过：无参数
- [ ] 服务器 `.env` 已加入 `TENCENT_SMS_PRINT_ALERT_TEMPLATE_ID` 与 `TENCENT_SMS_PRINT_RECOVERED_TEMPLATE_ID`（两个任意一个为空，对应的短信就不发，只记日志）
- [ ] `PRINT_ALERT_ENABLED` 为 True（默认），`PRINT_ALERT_SMS_DAILY_LIMIT` 保持默认 20 或按需调整
- [ ] 已重启后端并确认 `journalctl -u saas-base.service -n 20 --no-pager` 无异常
- [ ] **演练一次**：制造一个会失败的出票（例如临时配错 sn，仅在测试商户上），确认收到告警短信、恢复后收到恢复短信；演练后把配置改回并确认出票正常
- [ ] 确认接收短信的手机号是老板本人常用、会看的号码（用"已配置"表述，不要写出号码）

## 7. 顾客端小程序

- [ ] 新版本小程序已发布，**并记录版本号与服务端提交 `43f4e673` 的对应关系**（顾客文案和后端必须是同一代）
- [ ] 用真机扫桌码下单，确认文案与后台状态一致

## 8. 试点日

开启 PRINT_FIRST（**由运维人员做，一次只开一家店**）：

- [ ] 开启前再确认第 1–7 节全部完成
- [ ] 开启：把该店 `business_info["fulfilment_mode"]` 设为 `PRINT_FIRST`，核对租户前缀、只更新 1 行，改完读回确认
- [ ] 后台**刷新所有设备**（后台只在登录时读取一次模式，不刷新会看到旧界面）
- [ ] 开启后确认：后台没有"接单"和"批量接单"按钮；整桌结账可用
- [ ] 开启后第一单：真机下单，纸自动出，后台状态正确

店内人员规则（贴在打印机旁，口头也讲一遍）：

- [ ] 手机显示"有新订单"但**没有新纸**，马上检查打印机：有没有电、有没有纸、盖子关没关、网络是否正常
- [ ] 打印机重启 / 换纸之后，**主动数一下**：手机里最近的订单，每一单都有对应的纸吗？缺的用后台"补打"
- [ ] 补打前先看：纸是不是其实已经出来了（防重复）
- [ ] 打烊后断电的打印机，第二天开机后会自动补出前一晚的纸吗？**以第 5 节实测结论为准，不要凭印象**

退单规则（试点期间的统一做法，贴在店里，口头也讲一遍）：

系统现在**只支持**「商家还没开始制作」的已付款订单退单：先点**拒单**，再点**退款**，两步都要手动。**PRINT_FIRST 下订单一直是「待处理」，所以拒单始终可用**，这是目前唯一的退单路径。

- [ ] 出了纸的订单，**原则上不退单**。一定要退时，**先通知后厨**（口头 / 电话 / 叫人），再拒单。**系统不会通知厨房，也不会打印取消单**，不通知厨房就会白做、浪费食材
- [ ] 拒单之后，**必须马上点退款**，不能只拒单。只拒单，顾客的钱还扣着，顾客那边只看到「请联系商家」
- [ ] 退款点完后，看订单是不是显示「已退款」。显示「退款处理中」时，后台页面开着会自动向微信核对几次；还是处理中就**稍后刷新页面再看**。**系统没有接微信退款结果回调**，页面关掉或核对次数用完后不会自己更新，所以不要点完就走
- [ ] 顾客说「这个菜不要了 / 上错了」：系统**没有退菜和部分退款**。只能整单拒单、整单退款，再让顾客重新下单；或者店里自己处理（折扣、赠送），**不要在系统里私下改金额**
- [ ] 已经点了「开始制作」（WORKBENCH 模式才有）的订单，系统里**没有任何取消 / 退款入口**，只能店里和顾客协商，退款需要走微信商户平台人工处理，并记录这一单的订单号
- [ ] 后付（postpay / table_account）还没付钱的单：顾客能自己取消（待处理时），商家也能取消或拒单，不涉及退款
- [ ] 每天收档前，看一眼当天**已拒单但没有退款**的订单（订单页顶部会出现「资金异常 N笔需要退款」，点「查看订单」），一单都不能留

## 9. 随时回滚

- [ ] 回滚做法已演练：把该店 `fulfilment_mode` 改回 `WORKBENCH`，后台刷新所有设备，"接单"按钮恢复
- [ ] 回滚后，原来在 PRINT_FIRST 下停在"待处理"的订单，老板知道要怎么处理（接单后推进，或结账）

出现下面任何一种情况就**立刻回滚并停止试点**：

- 一单没出纸而店里没人发现，直到顾客问起
- 出现重复出纸，导致重复做菜
- 对账时发现金额不一致
- 老板或店员说"不会用 / 看不懂"

## 10. 试点期间每天要看的

- [ ] 当天订单数、已出票数（`print_status=SUCCESS`）、失败 / 未知数。三者对得上
- [ ] 有没有停在待处理很久的订单
- [ ] 打印告警短信有没有发出 / 有没有恢复短信
- [ ] 店员反馈：漏单、重复、不好用的地方

## 11. 目前已知的缺口（试点前必须有人拍板）

- 打印机离线 / 缺纸**还不能被系统可靠地发现**（见第 5 节与快麦对接说明）。试点只能依赖人工规则，除非先做"打印机健康检查"。
- **退单能力有限**：只支持待处理的已付款订单（拒单 → 退款）；开始制作后没有取消 / 退款 / 退菜 / 部分退款；拒单不会通知厨房，也不打印取消单；没有接微信退款结果回调，退款状态只靠页面自动核对几次或刷新。试点只能靠上面的「退单规则」人工兜底。
- 打印结果只到"下发成功"，没有"打印成功"的确认（没有 jobId，也没接回调）。
- 短信模板没通过审核之前，打印异常不会通知老板。
- 目前没有任何租户有真实流量，现有证据都来自测试商户。
