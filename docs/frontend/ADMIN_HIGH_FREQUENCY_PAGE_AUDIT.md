## 1. 审计结论

### 1.1 当前后台符合度评分

**审计范围符合度：61 / 100。结论：部分符合，状态确定性存在 P0 缺口。**

这不是整个 `admin-h5` 的视觉评分，也不是上一阶段 63 分设计成熟度的复算。它只衡量订单、Dashboard、菜品三页对当前治理合同的符合程度。

| 维度 | 权重 | 得分 | 核心判断 |
|---|---:|---:|---|

| 页面结构合同 | 20 | 14 | 三页都有可辨认的 Header/Content/Action/Feedback；页头未统一但合同不要求视觉同构，主要问题是动作拥挤和首页信息排序 |

订单是高频任务基础最好的一页；Dashboard 和菜品的主要失分不是外观，而是“页面显示的事实是否可信”。

## 2. 框架一致性审计

### 2.1 总体结论

| 页面 | Ant Design Vue PRIMARY | Vant LEGACY | 原生交互 | 判断 |
|---|---|---|---|---|
| OrderManage | Button、Card、Tabs、Input、Alert、Empty、Skeleton、Modal、Drawer 等均以 Ant 实现 | 无页面内 Vant 标签 | 3 个 link/date 类控件 | **基本符合**；原生按钮是否继续保留应按触摸范围判断 |
| Dashboard | Alert、Button、Card、Steps 等使用 Ant | `van-pull-refresh` 1 处 | 营业状态为带 `role=button` 的 span | **部分符合**；Vant 是既有 legacy，不是本阶段新增 |
| MenuManage | Button、Card、Tag、Drawer、Form、Switch、Dropdown、Modal 等以 Ant 实现 | 无页面内 Vant 标签 | 返回引导、售罄/恢复按钮及 file input | **部分符合**；售罄按钮在 Ant 可满足的场景复制了基础 Button 行为 |

证据：

- `admin-h5/src/main.js:18-19` 仍全局注册 Ant 与 Vant。
- `Dashboard.vue:3` 使用 `van-pull-refresh`；`git log -S "<van-pull-refresh"` 显示其来自历史提交 `f1fa123`。
- 当前三页相对 HEAD 均无工作区代码变更，因此没有发现 Constitution 建立后新增或扩大 Vant 的证据。
- `MenuManage.vue:106-110` 的售罄/恢复使用原生 button；`OrderManage.vue:141-146,379-384` 的桌牌更换使用原生 button。

治理判断：

1. **Ant PRIMARY：基本符合。** 三个页面的主要复杂交互均由 Ant 承担。
2. **Vant LEGACY：符合 Touch And Migrate。** Dashboard 的下拉刷新可继续存在；只有未来直接触摸该刷新能力时才评估迁移，禁止为清掉一个标签重写 Dashboard。
3. **原生 HTML：部分符合。** file input 属于框架明显不适合的合法场景；售罄/更换等原生按钮需要 focus、disabled、loading 与重复提交证据，当前实现不完整。
4. **PageHeader 不是框架违规。** 三页都没有使用共享 `PageHeader`，但合同要求的是逻辑结构和位置可预测，不要求所有页面强制换成同一组件。

## 4. 状态合同审计

### 4.1 P0：直接违反状态确定性的证据

#### A. 订单同步失败被显示为空，并可能提示“已刷新”

- `workbenchSyncCore.js:417-429` 捕获同步失败后返回 `{ ok:false }`，不会继续抛出。
- `OrderManage.vue:998-1001` 忽略返回结果，无条件执行 `message.success('已刷新')`。
- 初次同步失败后，core 在 `workbenchSyncCore.js:446-448` 结束 loading；订单数组仍为空。
- 页面只有连续失败 3 次后才显示网络 Alert（`OrderManage.vue:70-76`），在此之前 `OrderManage.vue:85-90` 会显示“今天还没有订单”。
- 历史订单失败也会清空数组（`OrderManage.vue:1079-1091`），同时模板显示“这一天没有订单”（`317-319`）。虽然有 error toast，但持续页面状态仍是 empty。

判断：**当前不符合**“error 不得显示为 empty”和“success 必须由结果确认”。这会让饭点老板误判“没有订单”或相信刷新成功。

#### B. Dashboard 统计业务错误会显示默认零值

- `Dashboard.vue:393-395` 在 `getDashboardStats()` 返回非 200 时只 `return`，没有抛错。
- `Promise.all` 因而可能继续成功，随后 `Dashboard.vue:415-416` 设置 `statsError=false` 和更新时间。
- `overview/stats/memberPulse` 初始值均为 0（`Dashboard.vue:165-178`）。

判断：**当前不符合**。业务错误可被显示成“今日营收 0 / 订单 0 / 会员 0”，并带“已更新”语义。

#### C. Dashboard 营销加载失败仍可显示“标准档运行中”

- `marketingPreview` 初始为空对象（`Dashboard.vue:431-433`）。
- `marketingEnabled` 使用 `enabled !== false`，空对象会推导为 true；强度缺失时默认 `standard`（`436-438`）。
- 请求失败被静默捕获，但 finally 仍设置 `marketingLoaded=true`（`451-459`）。
- 模板随后进入运行中分支并显示“标准档运行中”（`112-125`）。

判断：**当前不符合**“自动营销状态必须来自真实且成功获取的数据”。这是事实错误，不是普通 loading 样式问题。

#### D. Dashboard 打印机在首次请求前默认被视为异常

- `systemStatus.printer` 初始为 `warning`（`Dashboard.vue:186`）。
- `printerActionable` 对任何非 `ok` 的非空值返回 true（`246-248`）。
- 首次系统状态请求完成前，待办可短暂显示“打印服务异常”（`275-281`）。

判断：**当前不符合**。未知状态被当作已确认异常，可能产生假警报。

#### E. 菜品加载失败显示为空菜单

- `MenuManage.vue:848-855` 在 `getMenuItems()` 失败时执行 `allDishes=[]`。
- 页面 `MenuManage.vue:60-65` 随后展示“还没有菜品”和“添加第一道菜”。
- 页面没有 `menuError` 或等价状态。

判断：**当前不符合**，且与 Constitution 中针对菜品写明的 MUST NOT 完全冲突。

## 5. 高频任务效率审计

### 5.1 订单

#### 新订单发现：部分符合

已存在能力：

- 首页待办显示待接单数量并直达订单页（`Dashboard.vue:260-273`）。
- 底部“接单”Tab 有 pending badge（`components/TabBar.vue:92-95`）。
- 订单页顶部有待接单统计，当前/历史明确分开。
- 同步核心能检测新增 pending、播放声音并维护 highlight id（`workbenchSyncCore.js:266-287`）。

缺口：

- `OrderManage.vue` 没有消费 `isHighlighted`，新到订单卡没有短暂视觉标识。
- pending 订单按 FIFO 排序，保证先处理等待最久的单；这是合理的履约规则，但新到订单不会自动出现在 pending 队列最前。
- 声音未解锁时有明确 banner，这是正例；在静音环境中主要依靠数量变化和 Tab badge。

结论：能发现“有待接单”，但对“刚到的是哪一单”的识别仍是 P1 缺口。不得为了突出新单破坏 FIFO 履约顺序。

#### 接单和状态修改：基本符合

- 默认进入订单列表，接单/出餐按钮直接在卡片上，路径短。
- 接单、拒单、出餐、上菜、结账、退款均有 loading 或确认。
- 批量接单/出餐在桌台上下文显示数量。
- 失败后主动重拉服务端事实，资金和桌台冲突 fail closed。

缺口：单笔接单、出餐成功主要依赖卡片状态更新，没有独立成功文案；由于最终状态可见，这不构成 MUST 失败。真正需要修的是刷新失败仍提示成功。

#### 打印：符合异常处理合同，正常补打待业务确认

- `failed/unknown` 有文字 Tag、诊断信息和补打入口（`OrderManage.vue:164-177,200`）。
- 补打结果区分“已重新打印”和“结果仍未知”（`1384-1397`）。
- 正常订单没有补打入口。当前缺少商家频率、权限和审计证据，**不得**在审计阶段将其直接定为缺陷或新增按钮。

### 5.2 菜品

#### 搜索：当前不符合大规模可维护规则

主菜单只有分类筛选，没有菜品名称搜索。页面内“搜索”仅属于菜品库导入，不作用于当前门店菜单。500+ 菜品时，老板必须按分类滚动定位。

#### 编辑：基本符合

- 编辑入口直接位于菜品行，名称、图片、价格、分类、上下架、库存和规格集中在底部 Drawer。
- 核心字段优先，高级字段折叠；未保存离开有确认。
- 图片上传成功明确提示“点保存按钮生效”，不会把上传成功误报成菜品已保存。

#### 上下架：部分符合

- 单品售罄/恢复在列表一键完成，状态文字明确。
- 单品上架/下架需要进入编辑 Drawer；分类支持批量上下架。
- 分类批量操作成功后只改变页面状态，没有明确的成功提示；失败会提示并重拉。
- “售罄”和“下架”保持不同业务含义，这是符合项，不应为了统一合并。

### 5.3 Dashboard 第一屏信息价值

已存在能力：

- 门店营业状态、待接单、待结账、打印异常和今日经营结果均已存在。
- 待办点击可直达订单列表或桌台结账视图。
- 没有待办时待办区域不占空间。

缺口：

1. 模板顺序仍是 Hero → 套餐 → 待办 → 今日战报，套餐信息先于饭点行动。
2. 营销、会员、趋势等适合复盘，但首屏主路径同时承载过多类型数据。
3. 打印、营销和统计的默认/失败状态不可信，会降低第一屏信息价值。

结论：信息本身有价值，顺序和状态确定性不完全符合。下一阶段先修“真假”，再评估把套餐移到待办之后；禁止重画首页。

本次只建立构建资源基线，没有声明固定毫秒预算。没有冷启动设备数据、LCP/INP、API 分位和弱网瀑布时，MUST NOT 据此直接选择替换框架或重构页面。

### 6.2 Dashboard 请求数量

首次挂载触发 7 类请求：

1. 门店资料。
2. Dashboard 统计。
3. 今日订单。
4. 系统状态。
5. 营销预览。
6. 异常桌活动。
7. 当前套餐。

其中 `loadStats()` 同时等待统计和今日订单（`Dashboard.vue:390-420`），任一抛错会让整个统计区进入 error；其他次要请求多为静默降级。订单统计还会每 30 秒轮询。

风险判断：请求数量不是自动缺陷，但当前缺少 client/network/server 分段和弱网结果，无法判断应合并、延后还是保持并行。P0 只建立测量；P1 才根据数据处理请求编排。

### 6.3 订单大列表

已存在能力：

- 历史订单使用真实服务端分页，每页 20（`OrderManage.vue:1038-1095`）。
- 当前订单使用 full snapshot + cursor delta，同步频率和失败退避已有集中逻辑。
- 列表默认只渲染前 20 单（`1141-1146`）。

风险：

- 初始 full snapshot 请求当天订单全集，没有分页参数（`930-935`）。
- 搜索、状态筛选、排序、统计和桌台聚合仍在全量数组执行。
- 桌台视图对全部会话分组并渲染全部未结账桌台。

结论：DOM 有界化已经部分建立，但 1000+ 订单的网络、映射和聚合仍未有实测。先压测，再决定是否限制快照或改变派生策略。

### 6.4 菜品大列表

- `getMenuItems()` 不传搜索或分页参数（`MenuManage.vue:848-853`）。
- `allDishes` 保存全量菜品；分类和计数遍历全量数组。
- 模板对所有分类及每类全部菜品执行嵌套 `v-for`（`69-138`）。
- `dishesByCategory(cat)` 每次从全量数组 filter（`674-675`）。
- 没有主列表搜索、分页或窗口渲染。

结论：500+ 菜品是明确高风险，且先影响“找得到、改得了”，再影响滚动性能。下一阶段 MUST 先建立 500+ 数据基线和接口能力判断，禁止仅凭代码猜测直接上复杂虚拟列表。

### 6.5 API 与弱网边界

本次没有商家登录态、生产 API 样本、服务端耗时分位、真实设备或弱网会话，因此：

- 不给出 API P50/P95。
- 不给出白屏、LCP、INP 或路由可交互毫秒值。
- 不判断数据库、缓存或 SQL 是瓶颈。
- 只将“错误态不可信”和“数据处理无界”列为源码可证风险。

## 8. 下一阶段 Touch And Migrate 顺序

以下顺序每项都是独立小阶段，不应合并成一次改版。

### Touch 1：订单状态确定性

只触摸：初次同步、历史加载、手动刷新三类反馈。

- 区分 loading / empty / error。
- 只有同步结果成功才提示“已刷新”。
- 保留现有订单状态机、轮询、delta、退款、打印和桌台会话合同。
- 不拆 1933 行页面，不调整订单卡视觉。

### Touch 2：Dashboard 事实状态

只触摸：统计、营销、打印状态从“未知 → 成功/失败”的推导。

- 非 200 必须进入 error/unknown，不得保留默认成功语义。
- 自动营销必须在真实成功响应后才能显示运行档位。
- 打印状态初始为 unknown/loading，不得预设异常。
- 不重做 Dashboard 卡片，不迁移 Vant。

### Touch 3：菜品 error 与 empty 分离

只触摸：`loadMenu()` 和菜单主区状态。

- 请求失败保留 error 和重试路径。
- 只有成功返回空数组才显示“还没有菜品”。
- 不新增通用状态组件；优先使用现有 Ant Alert/Empty/Skeleton 能力。
- 不同时改搜索、分页、Drawer 或菜品卡视觉。

### Touch 4：建立性能与规模预算

只测量，不先重构：

- 冷启动首屏资源和可操作路径。
- Dashboard 7 类请求瀑布及 client/network/server 分段。
- 订单 1000+ 的 full snapshot、筛选、排序、聚合和 DOM。
- 菜品 500+ 的返回体、分类计算、渲染和查找任务。
- 弱网、超时、断网恢复和重复提交。

记录基线、预算和超限决策后，才能进入下一项。

### Touch 5：菜品大规模可维护

根据 Touch 4 证据选择最小方案，优先保证名称可搜索和结果可达。若需要接口参数，必须保持旧接口兼容；禁止直接引入复杂虚拟列表或新框架。

### Touch 6：订单 1000+ 与新单识别

在不破坏 FIFO 的前提下治理新单识别；只有压测证明 full snapshot 或派生计算超预算时，才限制对应边界。不得同时重做桌台视图和订单状态机。

### Touch 7：Dashboard 信息顺序与请求编排

先把待办置于套餐等商业曝光之前；再根据真实瀑布决定哪些请求延后或解耦。不得为了减少请求数删除商家必需状态。

### Touch 8：P2 局部视觉债务

只在相关功能被再次触摸时处理 Vant 下拉刷新、原生按钮、头部点击区域和局部样式。未触摸部分允许保持现状，不建立新组件库，不一次性统一三页。
