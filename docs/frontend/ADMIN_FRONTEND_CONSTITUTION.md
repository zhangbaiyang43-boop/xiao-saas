# 商家后台前端治理合同

```text
VERSION=V1.0
PHASE=P1-ADMIN-FRONTEND-CONSTITUTION-PHASE-01
SCOPE=admin-h5
TYPE=ADMISSION_CONTRACT
UI_PRIMARY=Ant Design Vue
UI_LEGACY=Vant
MIGRATION=TOUCH_AND_MIGRATE
```

本文是 `admin-h5` 后续开发和维护的准入规则。它基于 [ADMIN_FRONTEND_DESIGN_AUDIT.md](./ADMIN_FRONTEND_DESIGN_AUDIT.md) 建立，但不重复审计结论。

本文不是完整 Design System，不是组件库，不是视觉规范，也不声明新的组件、Token 或业务状态。业务页面当前长什么样，不自动成为后续页面的标准。

## 0. 合同效力

规则强度：

- **MUST**：必须满足；不满足时不得按常规变更合入，除非存在已记录并获批准的例外。
- **SHOULD**：默认应满足；偏离时必须说明对商家任务、兼容性或工程成本的具体理由。
- **MUST NOT**：明确禁止；不得以“历史页面已经这样做”为新增依据。

权威顺序：

1. 支付、退款、订单状态机、权限和接口字段等既有业务合同。
2. 本治理合同。
3. Ant Design Vue 现有能力、`admin-h5` 已确认的公共结构与运行时样式权威。
4. 被触摸页面的局部实现。
5. 未触摸的历史实现；它可以继续存在，但不是新代码的设计依据。

发生冲突时，低位规则 MUST 服从高位规则。本合同 MUST NOT 被用于绕过资金、订单、权限、数据库或 API 合同。

## 1. 产品定位

### 1.1 服务对象

`admin-h5` 服务于：

- 餐饮老板：关注经营结果、异常和关键配置。
- 店长：关注当班运营、订单处理、商品可售状态和员工协作。
- 店员：关注当前任务、下一步动作和操作结果。

页面 MUST 使用目标岗位能理解的餐饮业务语言。技术字段 SHOULD 解释“从哪里获取、会影响什么、错误后如何恢复”。

### 1.2 核心目标

商家后台 MUST 以以下目标排序：

1. 提高经营效率。
2. 降低操作成本和学习成本。
3. 保证业务、资金、设备和保存状态的确定性。

高频任务 SHOULD 在最短合理路径内完成，但 MUST NOT 以减少点击为由跳过必要的确认、权限、审计或结果反馈。

### 1.3 与消费者端的区别

消费者端优先体验、转化和简单；商家端优先效率、准确和稳定。

- 商家页面 MAY 使用更高的信息密度，但 MUST 依靠分组、对齐和信息层级提高密度，MUST NOT 依靠过小文字或过小触控区域。
- 商家页面 MUST 优先回答“现在要处理什么、当前是什么状态、操作是否成功”。
- 消费者端的转化布局、营销表达和视觉原语 MUST NOT 被直接复制为商家后台规则。

## 2. UI 框架治理

### 2.1 Ant Design Vue — PRIMARY

Ant Design Vue 是 `admin-h5` 的主 UI 框架。

- 新增页面和新增交互 MUST 优先使用 Ant Design Vue 已有能力。
- 被触摸页面新增 Button、Card、Form、Input、Select、Modal、Drawer、Table、Empty、Skeleton、Alert 等基础能力时，MUST 首先判断 Ant Design Vue 是否满足需求。
- 页面 SHOULD 直接使用框架能力；MUST NOT 仅为改名或统一外观再包一层无业务语义的组件。
- 框架组件的选择 MUST 服从移动端触控、任务效率和信息可读性，MUST NOT 因为组件存在就机械使用 PC 表格或密集工具栏。

### 2.2 Vant — LEGACY

Vant 是历史兼容框架，不是新增标准。

- 未触摸或仅做必要修复的 Vant 页面 MAY 继续使用现有 Vant 组件。
- 触摸旧页面时 SHOULD 只迁移与本次需求直接相关的交互，不要求全页替换。
- 新页面 MUST NOT 引入 Vant。
- 旧页面 MUST NOT 因新增功能继续扩大 Vant 的组件种类或使用边界；确有兼容性阻塞时必须记录例外。
- 团队 MUST NOT 发起一次性 Vant 全量替换。

### 2.3 原生 HTML

原生 HTML MAY 用于：

- 语义结构，例如 `main`、`section`、`header`、`nav`、标题、段落和列表。
- 简单、无状态的内容展示。
- Ant Design Vue 明显不适合，且原生语义能更直接满足任务的轻量场景。

使用原生交互控件时：

- MUST 提供明确的 focus、disabled、loading（如适用）、点击反馈和可访问名称。
- MUST 保证移动端可操作性，不得用视觉尺寸压缩触控区域。
- SHOULD 记录框架不适合的具体原因。
- MUST NOT 自行复制 Button、Card、Form、Input、Select、Modal、Drawer、Table、Empty 等通用基础组件。
- MUST NOT 通过页面 CSS 制造第四套基础组件体系。

## 3. 页面结构合同

页面的逻辑结构 SHOULD 遵循：

```text
PageHeader
    ↓
Content
    ↓
Action
    ↓
Feedback
```

这不是固定 DOM 顺序，也不是要求所有页面视觉相同；它要求信息和行为位置可预测。

### 3.1 PageHeader

- MUST 说明当前页面或当前任务。
- 有返回路径时 MUST 提供可预测的返回行为。
- 页面级动作 SHOULD 放在稳定位置，且 MUST 明确主次。
- MUST NOT 在窄屏头部并列堆放多个同等强调的小按钮。

### 3.2 Content

- MUST 优先展示完成当前任务所需的信息。
- SHOULD 按“待处理 → 当前事实 → 复盘信息”的顺序组织。
- MUST NOT 让套餐、营销说明或装饰内容遮挡订单、异常、保存结果等行动信息。
- 列表或详情中的关键状态 MUST 使用文字表达；颜色只能辅助，MUST NOT 成为唯一信息载体。

### 3.3 Action

- 同一操作区域 SHOULD 只有一个最高优先级动作。
- 高频、低风险动作 SHOULD 缩短路径；资金、删除、退款、密钥等高风险动作 MUST 保留确认和结果反馈。
- 动作触发后 MUST 防止不可识别的重复提交。
- 固定底部动作 MUST 处理安全区，且 MUST NOT 遮挡内容或反馈。

### 3.4 Feedback

- 异步动作 MUST 产生与结果一致、商家可见的反馈。
- 字段错误 SHOULD 靠近字段；页面级失败 SHOULD 出现在当前任务上下文中；短暂结果 MAY 使用全局消息。
- 反馈 MUST 说明“发生了什么”和“下一步能做什么”。
- Toast MUST NOT 代替需要持续可见的错误、过期数据或未保存状态。

## 4. 状态合同

`loading`、`empty`、`error`、`success` 是四种不同事实，MUST 分开建模和展示。

| 状态 | 唯一定义 | MUST | MUST NOT |
|---|---|---|---|
| `loading` | 数据正在获取或操作正在提交 | 保留任务上下文；提交动作防重复；必要时说明正在处理 | 显示为 0、空列表或可重复提交的默认按钮 |
| `empty` | 请求成功，但没有符合条件的数据 | 说明为空的范围；条件筛选导致为空时提供清除或返回路径 | 用于接口失败、超时、无权限或解析失败 |
| `error` | 请求失败、响应不可用或结果无法确认 | 显示失败事实；可恢复时提供重试；保留仍可信的旧数据并标记可能过期 | 清空为“暂无数据”；伪装为成功；凭默认值推断业务状态 |
| `success` | 操作已被后端或既有业务合同确认完成 | 呈现最终结果；更新相关状态；关闭 loading | 保存失败仍保持已保存外观；只因前端状态已改变就宣告成功 |

补充规则：

- 接口失败 MUST NOT 显示为空列表或“暂无数据”。
- 保存失败 MUST 回滚乐观状态，或持续明确显示“未保存/结果未知”；MUST NOT 保持成功状态。
- 页面含多个独立数据区时，非关键区失败 MAY 局部降级，但 MUST 标明该区域未更新；MUST NOT 把局部失败扩散为高频任务不可用。
- 弱网下已有可信数据 MAY 保留，页面 MUST 标注更新时间或过期风险。
- 成功反馈 SHOULD 与动作风险匹配：普通保存可短暂提示，高风险操作的结果 SHOULD 持续可确认。

## 5. 高频业务规则

### 5.1 订单

- 新订单 MUST 明显，并能与历史订单、已处理订单区分。
- 订单、支付、退款、出餐、桌台和打印状态 MUST 使用明确文字。
- 接单、拒单、出餐、结账、退款和打印等动作 MUST 展示处理中、成功或失败结果。
- 打印失败或打印状态未知 MUST 可识别，并 SHOULD 提供符合既有权限和业务合同的恢复路径。
- 订单辅助数据、经营统计或营销请求失败 MUST NOT 阻塞接单主路径。
- 批量动作 MUST 明确作用范围和不可逆后果。
- MUST NOT 未经业务确认新增或改变正常补打、退款、支付和订单状态机能力。

### 5.2 菜品

- 菜品的可售、售罄、上架、下架和库存状态 MUST 明确，MUST NOT 把不同业务状态合并为同一含义。
- 菜品加载失败 MUST 显示 `error`，MUST NOT 显示为空菜单。
- 新增、改价、换图、售罄、恢复和上下架 MUST 有明确结果反馈。
- 大规模菜品场景 MUST 保持可搜索、可定位、可维护；MUST NOT 依赖无限滚动浏览全部菜品完成高频修改。
- 500+ 菜品的方案 MUST 先测量接口、数据处理和渲染成本，再选择服务端搜索、分页、分段渲染或其它兼容方案。

### 5.3 会员

- 会员数据 MUST 可通过真实服务端能力搜索和到达。
- 分页 MUST 真实有效；前端切片 MUST NOT 被表述为服务端分页。
- 列表总数、当前范围和“加载更多”行为 MUST 与接口事实一致。
- 发券、积分调整、停用和恢复 MUST 展示可信结果；失败 MUST NOT 保持已完成外观。
- 大会员库 MUST NOT 通过一次请求加载全部会员，也 MUST NOT 因固定请求上限导致后续会员不可达。

### 5.4 营销

- 自动营销是否运行 MUST 来自真实且成功获取的数据。
- 加载失败、状态未知或数据过期时 MUST 显示不确定状态，MUST NOT 使用默认值宣告“运行中”。
- 发券数量、核销、成本、GMV 等指标 MUST 标明统计范围和时间范围。
- 营销文案 MUST NOT 做当前系统和数据无法证明的绝对承诺。
- 策略配置 SHOULD 优先使用老板可理解的业务结果，并将高级参数渐进展示。

## 6. 性能治理

性能治理 MUST 遵循：

```text
建立基线 → 声明预算 → 按同一方法测量 → 判断是否超限 → 小步处理并复测
```

本合同不写固定毫秒。每个性能阶段 MUST 根据设备、网络、数据规模和当前生产构建建立可复现基线，再声明该阶段预算。没有测量数据时 MUST NOT 以猜测决定优化方向。

| 领域 | 预算必须覆盖 | 测量方法 | 超限处理 |
|---|---|---|---|
| 首屏资源 | 入口 JS/CSS、共享 vendor、重复 UI 框架成本、关键字体/图片 | 生产构建产物；冷缓存；记录 raw/gzip 和资源请求瀑布 | 先定位新增来源；SHOULD 优先移除非关键首屏依赖或延后加载；MUST NOT 先换框架 |
| 路由加载 | 高频路由 chunk、依赖加载、首次可操作前的阻塞任务 | 生产构建分包；登录后首次进入；目标设备性能记录 | 拆分非关键能力或延迟次要模块；MUST 保持任务主路径完整 |
| 大列表 | 返回条数、DOM 数量、映射/筛选/聚合成本、滚动和操作响应 | 至少覆盖订单 1000+、菜品 500+、会员 10000+ 的可重复数据场景 | 优先保证数据可达和结果正确，再选择分页、搜索或窗口化；MUST NOT 一次加载全部数据掩盖问题 |
| API 耗时 | 首页、订单、列表和保存动作的 client/network/server 分段与失败率 | 使用真实接口或可说明的等价环境；记录样本、分位和响应体积 | 先确定瓶颈归属，再处理请求编排、返回规模或服务端问题；MUST NOT 仅凭感觉优化 SQL 或缓存 |
| 弱网场景 | 白屏、可操作性、超时、重试、旧数据、重复提交 | 冷启动、限速/高延迟/断网恢复；覆盖真实移动设备或明确设备档位 | 核心任务 SHOULD 优先可用；次要区域 MAY 降级；MUST 显示数据新鲜度和失败事实 |

性能预算记录 MUST 包含：基线版本、测试环境、数据规模、预算边界、实测结果和超限决策。环境或口径不同的数据 MUST NOT 被直接比较。

性能优化 MUST 保持接口字段、业务状态机和旧逻辑兼容。为了缩小包体或加快渲染，MUST NOT 删除商家必需信息或反馈。

## 7. Touch And Migrate

```text
NEW_CODE=MUST_COMPLY
TOUCHED_LEGACY=MIGRATE_IN_SCOPE
UNTOUCHED_LEGACY=MAY_REMAIN
BIG_BANG_REWRITE=MUST_NOT
```

- 新代码 MUST 遵守本合同。
- 修改旧页面时，MUST 迁移本次需求直接触摸的结构、状态或交互；SHOULD 保持范围最小。
- 未触摸页面 MAY 保持现状，历史存在不构成违规，也不构成新标准。
- 迁移 MUST 以商家任务改善或风险降低为目的，MUST NOT 以“代码看起来统一”为唯一理由。
- 若合规需要跨越多个业务模块、改变 API/数据库或重做状态机，当前变更 MUST 停止扩张并拆成独立阶段。
- 每次迁移 SHOULD 说明：触摸范围、保留的旧行为、验证方式和未处理债务。

## 8. MUST NOT：禁止事项

`admin-h5` 后续开发和维护 MUST NOT：

1. 引入第三套 UI 框架。
2. 建立新的通用组件库或复制 Ant Design Vue 的基础组件。
3. 复制消费者端 `FRONTEND_CONSTITUTION.md`、转化布局或视觉规则作为后台标准。
4. 为了统一而统一，包括无业务收益的全量改名、全量包裹、全量换色和全量结构替换。
5. 一次性替换全部 Vant、原生交互或历史页面。
6. 发起后台大重构，或在单一需求中同时重做多个业务模块。
7. 以本合同为由新增 Token、修改业务状态、数据库结构或 API 字段。
8. 把加载失败、超时、无权限、解析失败显示为 `empty`。
9. 在没有测量数据时猜测性能瓶颈并展开大范围优化。
10. 用视觉一致性覆盖订单、支付、退款、打印、权限和保存结果的确定性。

## 9. 当前后台治理路线图

路线图描述后续执行顺序，不授权本阶段修改业务代码。

### P0：建立治理入口、状态正确性和性能基线

- MUST 把本合同作为 `admin-h5` 新增和触摸变更的评审入口。
- MUST 优先处理“错误被显示为空”“保存失败仍像成功”“真实数据不可达”等状态正确性问题。
- MUST 为首屏资源、路由、大列表、核心 API 和弱网建立可复现基线与阶段预算。
- SHOULD 先覆盖 Dashboard、OrderManage、MenuManage、CustomerList 和营销运行状态。
- MUST NOT 在基线前启动框架替换或大规模性能重构。

### P1：治理订单、菜品、会员和营销高频任务

- 订单：SHOULD 缩短饭点主路径，保持状态、打印和操作结果确定。
- 菜品：SHOULD 建立失败态与空态分离，并保证 500+ 菜品可定位和维护。
- 会员：MUST 使用真实搜索和分页能力，保证 10000+ 数据场景可达。
- 营销：MUST 以真实数据展示运行状态，并收敛无法证明的承诺。
- 触摸超大页面时 SHOULD 小步拆出纯逻辑或独立业务块，MUST NOT 借机重写整个页面。

### P2：偿还视觉和历史维护债务

- SHOULD 按被触摸页面逐步处理 PageHeader、状态反馈、触控区域、间距、圆角和暗色一致性。
- 无引用组件 MUST 在确认无动态依赖并单独评审后再清理。
- 历史代码清理 MUST 有可验证收益，MUST NOT 与高风险业务改动捆绑。
- SHOULD 建立周期性的资源体积、大列表和高频任务回归记录。

## 10. 例外与准入检查

无法遵守 MUST 或 MUST NOT 时，变更记录 MUST 包含：冲突规则、业务原因、限定文件、影响范围、临时或永久、验证方式；临时例外还 MUST 包含退出条件。未记录的例外视为未批准。

提交 `admin-h5` 前 SHOULD 回答：

1. 是否优先使用 Ant Design Vue，并避免扩大 Vant？
2. PageHeader、Content、Action、Feedback 是否可预测？
3. loading、empty、error、success 是否表达真实且不同的状态？
4. 高频任务是否更短、更明确，同时保留必要确认？
5. 大列表是否真实可达，而非只在前端切片？
6. 性能判断是否有同口径基线和预算？
7. 是否只迁移本次触摸范围？
8. 是否保持接口字段、数据库、权限、资金和业务状态机不变？
