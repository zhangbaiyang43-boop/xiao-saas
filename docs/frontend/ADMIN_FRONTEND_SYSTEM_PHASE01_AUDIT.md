## 1. 当前后台前端现状

### 1.1 产品形态与总体判断

`admin-h5` 已经不是一个只有 CRUD 的初始后台。它具备老板工作台、订单履约、桌台处理、菜品维护、会员经营、
营销、门店设置，以及前台、服务员、后厨的角色工作台。底层工程能力相对完整，部分核心页面也已经形成面向餐饮任务的
表达方式。

当前不足不在于“没有页面”，而在于这些能力还没有形成可持续复用的后台前端系统：

- 工程底座统一，但页面层的任务结构、状态表达和视觉语言仍依赖各页面自行实现；
- 订单和 Dashboard 已有较强的业务语义，菜品、会员、营销仍有明显的数据可达性和状态真实性缺口；
- 已有组件中既有有效业务组件，也有无静态引用、依赖痕迹不完整的历史组件；
- 已有设计变量和全局样式，但存在两套颜色语义，尚不能称为成熟 Design System；
- 性能观测合同已经闭环，但 production 样本不足，尚未获得优化授权。

### 1.3 路由与导航结构

老板默认底部导航为“今日、接单、菜单、更多”，员工按角色进入前台、服务员或后厨工作台。这一结构正确地把高频履约任务
放在一级导航中，避免把组织后台的全部模块平铺给店员。

当前路由同时包含经营、履约、会员、营销、设置和组织管理。路由权限已经结构化，但“更多”仍承担大量入口的聚合责任。
后续信息架构治理 SHOULD 以角色 Jobs 和使用频率整理入口，不应按数据库对象或已有路由文件名机械分组。

### 1.4 状态管理与请求边界

Pinia 当前只承载身份和权限等跨页面状态，这是合理边界。订单同步使用 composable 和轮询管理器，避免全部塞入全局 store。
问题是 OrderManage、MenuManage 等页面同时承担数据获取、映射、状态机、表单、弹层、批量动作和大量视觉样式，局部状态虽不
“混乱”，但已经超过单文件可安全理解的规模。

Axios 统一入口是现有架构的重要资产。它解决了鉴权、超时、403/401、轮询重复请求和性能记录，但不会统一把 HTTP 200 中的
业务失败转换为异常。因此页面必须检查 `res.code`。当前不同页面执行不一致，是多处错误态和假成功的根源之一。

### 1.5 组件现状

当前组件可分为三类：

| 类型 | 示例 | 当前判断 |
| --- | --- | --- |
| 有复用价值的页面基础 | `PageHeader`、`TabBar`、`NavBar` | 已存在，但 PageHeader 只覆盖部分二级页 |
| 已证明的业务组件 | `StatCard`、`InsightCard`、`WorkbenchSyncBar`、`AssistedOrderSheet`、`PickupNoPicker` | 有真实消费者，应保留并按触摸迁移治理 |
| 待核实历史组件 | `ListState`、`PaginationBar`、`CustomTable`、`CustomCheckbox`、`CustomDatePicker`、`CustomRadio` | 静态搜索无页面消费者或仅被索引导出，部分模板含未声明的 Element Plus 标签；不能直接删除，需在 Phase-04 单独审计 |

当前没有一套统一的 Button、Card、Form、Modal 复制品，这是好事。大部分高频页直接使用 Ant Design Vue。与此同时，页面仍大量
自行书写卡片、筛选 chip、状态条、空态和按钮样式，同类语义并未完全统一。

### 1.6 设计语言现状

`global.scss` 已有品牌色、文字色、背景、边框、圆角、状态和暗色模式等 CSS 变量，也包含公共页面间距、卡片、状态和动画规则。
这说明设计语言不是从零开始。

但 `variables.scss` 仍保留靛蓝色和渐变为主的旧 Sass 变量，而当前 CSS 变量以微信绿为品牌色。两套变量并存，且页面内还有大量
内联色值、圆角和间距。当前成熟度应评为“部分存在”，不能称为单一可信 token 源。

动画已有 `prefers-reduced-motion` 降级，这是积极能力。商家后台后续 MUST 将动画限制在状态变化和轻量反馈，不得让错落入场
影响高频操作速度。

## 2. 当前问题分类

本节的 P0/P1/P2 是问题严重度。第 7 节的 P0/P1/P2 是页面迁移波次，两者用途不同。

### 2.1 P0：状态真实性与经营安全

| 问题 | 当前证据 | 商家影响 | 准入要求 |
| --- | --- | --- | --- |
| 菜品加载失败显示为无菜品 | `loadMenu()` catch 清空数组，但模板只有 loading、empty、list | 老板可能误以为门店菜品被清空 | MUST 增加独立 error 状态，失败不得进入 empty |
| 会员业务失败显示为空 | `res.code !== 200` 时清空列表并 return，但未设置 `loadError` | 会员资产看似归零，产生经营恐慌 | MUST 将 HTTP 成功中的业务失败也映射为 error |
| 优惠券列表失败可落入空态 | 首次加载 catch 只 toast，`templates` 仍为空，随后显示“还没有手动建券” | 无法区分没有券与加载失败 | MUST 保留可重试错误态，不得使用空态代替失败 |
| 营销预览失败仍宣称运行中 | CouponCenter 顶部固定显示“自动运行中”，预览失败被静默吞掉，默认档位为标准，统计默认 0 | 商家会相信无法证明的运行状态和结果 | MUST 以真实数据确认 enabled、档位和统计；未知时明确未知 |
| 部分保存动作只依赖异常，不校验业务 code | Dashboard 营业状态、营销开启及部分菜品动作直接成功提示或本地更新 | 后端拒绝但页面可能显示成功 | MUST 在动作反馈前确认合同中的真实成功字段 |

已确认当前 OrderManage 会区分首次失败、旧数据同步失败、loading 和 empty，手动刷新失败不会显示“已刷新”；Dashboard 统计、
营销状态和打印机未知也已具备显式错误或未知表达。这些能力 MUST 保持，不得在后续视觉调整中回退。

### 2.2 P1：高频任务效率与数据可达性

| 问题 | 当前证据 | 商家影响 |
| --- | --- | --- |
| 菜品主列表没有按名称搜索 | 搜索只存在于“菜品库导入”弹层，主列表只有分类筛选 | 500+ 菜品时修改价格或上下架难以定位 |
| 菜品全量加载、全量渲染 | 所有分类与所有菜品行一次渲染 | 大规模菜品的 DOM、图片和滚动风险高，真实归因仍待样本 |
| 会员只取第一页 100 条 | 固定 `page=1,page_size=100`，本地每次展示 30，无法请求下一页 | 10000+ 会员中第 101 条以后普通浏览不可达 |
| 会员经营信息不足 | 列表主要展示身份、来源、最近到店标签和发券 | 缺少可执行分层、消费价值和批量经营入口 |

| 营销效果缺少“结果到动作”闭环 | 营销效果页展示窗口和指标表，成功但无数据时没有专用 empty，且没有下一步建议 | 老板看到数据后仍不知道该保持、暂停还是调整 |

### 2.3 P2：一致性与长期维护债务

| 问题 | 当前证据 | 原则 |
| --- | --- | --- |
| Ant 与 Vant 并存且均全局注册 | `main.js` 同时 `app.use` 两套框架 | Vant 作为 legacy 维持，不扩大，不因统一发起替换工程 |
| 页面结构执行不一致 | 二级页部分使用 PageHeader，高频页常自行实现 header | 统一信息位置合同，不强制视觉外观相同 |

## 3. 后台前端系统目标

未来 `admin-h5` 应成为一个面向餐饮现场的移动经营工作系统，而不是把 PC ERP 缩小到手机，也不是把消费者小程序换一套文案。

目标产品应满足：

1. **老板看结果**：进入页面先知道经营结果、异常和最值得做的下一步。
2. **店长控现场**：订单、桌台、库存、员工和设备状态清晰，异常可以马上定位和处理。
3. **店员做单一任务**：按角色只看到当前职责所需的最短路径，不承担老板的全部配置复杂度。
4. **系统说真话**：未知就是未知，失败就是失败，不用 0、空列表或“运行中”掩盖不确定性。
5. **高频操作可预测**：标题、主要内容、关键动作和反馈位置稳定，忙时不需要重新学习。
6. **数据规模可持续**：订单、菜品和会员增长后仍能查找、分页、定位和操作，而不是靠减少可达数据维持流畅。

系统成功标准不是页面更漂亮，而是发现问题时间更短、完成任务步骤更少、误操作更少、状态争议更少。

## 4. 后台设计原则

### 4.1 Jobs 原则

每个页面在设计、开发和评审时 MUST 先写清楚一句 Jobs Statement：

> 当我处在什么经营场景时，我需要完成什么任务，从而得到什么确定结果。

| 页面 | 核心 Job | 首要成功信号 |
| --- | --- | --- |
| Dashboard | 当我开始营业或巡店时，快速确认今天经营结果、当前异常和下一步动作 | 异常先被看到，今日核心结果可信，动作可直达 |
| OrderManage | 当订单进入和流转时，快速接单、出餐、结账、处理打印或支付异常 | 新订单不遗漏，状态不含糊，操作结果可确认 |
| DishManage | 当供应、价格或商品信息变化时，快速找到目标菜品并完成维护 | 可搜索定位，供应状态明确，保存结果可信 |
| MemberManage | 当我需要服务或经营会员时，快速找到人、理解价值并执行合适动作 | 数据可达、分层可理解、动作可追踪 |
| Marketing | 当我投入优惠成本时，知道系统在做什么、带来什么结果、是否需要调整 | 运行状态真实，成本和效果可解释，决策有下一步 |

任何模块如果不能支持本页核心 Job，SHOULD 降级、折叠或移出首屏。

### 4.2 OPPO Less but Better 原则

这里的 OPPO 原则不是复制消费者端视觉，而是约束 B 端复杂度：

- MUST 减少无效信息：正常系统状态静默，异常和待处理优先；
- MUST 减少无效操作：同一任务只保留一个主入口，危险动作与高频动作分离；
- MUST 减少无效状态：不展示无法由真实数据证明的“运行中”“正常”“0”；
- SHOULD 使用渐进披露：高级参数、低频配置和审计信息在需要时展开；
- SHOULD 让默认路径覆盖大多数老板，专业能力仍可在次级入口访问；
- MUST NOT 以删掉必要信息为“极简”，准确性和可追溯性优先于视觉简洁。

### 4.3 B 端信息优先级

页面信息优先级固定为：

`异常和风险 > 当前待办 > 今日/当前结果 > 趋势与解释 > 低频配置 > 系统说明`

同一屏出现多个动作时：

- MUST 只有一个与当前 Job 直接相关的主动作；
- SHOULD 将次要动作放入次级按钮、更多菜单或后续步骤；
- MUST 将不可逆动作与高频动作拉开距离并二次确认；
- MUST 保留操作中、成功、失败和回滚后的明确反馈。

### 4.4 视觉语言原则

- **信息密度**：移动端一屏优先容纳一组可扫描的结果或任务，不追求 PC 表格密度，也不使用消费者端大面积营销留白。
- **层级**：标题说明当前位置，业务摘要说明结果，主任务区承载操作。装饰不得抢过异常和主动作。
- **颜色**：品牌绿用于主动作和已确认的积极状态；红色只用于危险、失败和需立即处理；橙色用于警告或待确认；正常状态优先中性表达。
- **未知状态**：未知 MUST 使用“未知、未确认、加载失败”等文字，不得借用成功绿或错误红假定结果。
- **留白**：沿用现有间距基线，按信息组分隔。不得为了“高级感”扩大留白导致操作滚动距离增长。
- **字体**：金额、数量和状态优先可扫读；说明文字降级但保持可读。不得用字号差异代替完整信息结构。
- **动效**：只用于状态变化和轻量反馈，必须尊重 reduced motion；不得阻塞接单、切换和保存。
- **框架**：Ant Design Vue 是 PRIMARY；Vant 是 LEGACY。原生 HTML 只用于语义结构、简单无状态展示或框架明显不适合的场景。

## 5. 页面系统规范

### 5.1 统一逻辑结构

所有新增页面和被需求触摸的旧页面 MUST 按以下逻辑检查：

```text
PageHeader
    ↓
Business Summary
    ↓
Main Task Area
    ↓
Action
    ↓
Feedback
```

这不是强制所有页面长得一样，也不要求每一层都成为独立 Vue 组件。目标是让信息位置可预测。

| 区域 | 必须回答 | 规则 |
| --- | --- | --- |
| PageHeader | 我在哪里？当前上下文是什么？ | 标题稳定；高频全局动作最多保留必要项；返回和权限明确 |
| Business Summary | 现在结果如何？有什么异常？ | 只放影响当前 Job 的摘要；失败不得显示默认值 |
| Main Task Area | 我来这里主要处理什么？ | 主列表、工作台或核心表单占据页面主要注意力 |
| Action | 下一步可以做什么？ | 主动作靠近对象；批量、危险和低频动作分级 |
| Feedback | 系统是否真的完成？ | loading、empty、error、success 和 unknown 明确且互斥 |

### 5.2 页面状态合同

| 状态 | 含义 | 页面要求 |
| --- | --- | --- |
| loading | 正在获取或提交 | 保留任务上下文，防止重复提交，不提前展示结果 |
| empty | 请求成功且确认没有数据 | 解释为什么为空，并给出与 Job 相关的下一步 |
| error | 请求或业务合同失败 | 不进入 empty，保留旧数据时标记“上次数据”，提供可执行重试 |
| success | 服务端确认操作完成 | 提示结果，并同步可信页面状态 |
| unknown | 当前无法证明真实状态 | 明确“未确认”，不得映射为正常、异常或运行中 |

页面评审 MUST 同时覆盖 HTTP 异常和 HTTP 200 但业务 `code` 失败的场景。

第一眼已经可以看到门店、营业状态、可行动待办和今日营收。页面明确回答了“今天经营如何”和“当前异常是什么”，

支持老板决策。

#### OrderManage

新订单提醒、待发桌牌、桌台状态、列表搜索、状态筛选、接单、出餐、上菜、结账、打印未知/失败、退款和同步失败均有明确表达。

摘要、分类、售罄、恢复供应、上下架、编辑、复制和导入能力较完整，也将删除收进更多菜单。最大问题是大规模菜品的“找到目标”

#### Marketing

MarketingEffectiveness 能区分 loading/error，并提供 7/30/90 天窗口，但成功无数据缺少 empty，指标没有转化为保持、调整或停止的
下一步建议。营销系统首先要可信，其次才是更丰富的创建能力。

## 6. 组件系统规划

本规划不是批准建立新组件库。Phase-02 的任务是建立组件准入和复用合同，优先使用 Ant Design Vue 与现有有效组件。

### 6.1 Level 1：基础能力层

范围包括 Button、Card、Form、Input、Table/List、Modal/Drawer、Empty、Loading、Alert、Message。

- MUST 直接优先使用 Ant Design Vue；
- MUST NOT 再包装一套只改颜色和圆角的基础组件；
- Vant 现有页面允许维护，但新页面 MUST NOT 扩大 Vant；
- 原生 HTML MUST NOT 复制 Button、Card、Form 等基础能力；
- 现有 CSS 变量先盘点消费者和冲突，再确定唯一来源，本阶段不新增 token。

### 6.2 Level 2：业务组件层

业务组件必须表达稳定业务语义，而不是视觉容器。例如：

- 经营数据摘要：现有 `StatCard`、`InsightCard`；
- 履约同步与异常：现有 `WorkbenchSyncBar`；
- 订单现场动作：现有 `AssistedOrderSheet`、`PickupNoPicker`；
- 角色导航：现有 `TabBar`。

新增或提升业务组件前 MUST 同时满足：

1. 至少两个真实页面或两个稳定业务场景需要同一语义；
2. 状态合同一致，而不只是外观相似；
3. API 和业务决策仍由页面或业务层负责；
4. 抽取能减少误差或重复维护，而非只减少几行模板；
5. 有测试或明确验收覆盖 loading、empty、error、success、unknown。

### 6.3 Level 3：页面模板层

页面模板首先是评审清单，不一定是 Vue 组件：

| 模板 | 适用场景 | 核心结构 |
| --- | --- | --- |
| Workbench | Dashboard、订单、角色工作台 | 异常/待办、结果摘要、主任务、反馈 |
| Manage List | 菜品、会员、券记录 | Header、搜索/筛选、摘要、列表、分页/加载、状态 |
| Detail/Edit | 菜品编辑、会员详情、设置 | 上下文、关键字段、渐进设置、保存、离开保护、反馈 |
| Effect/Insight | 营销效果、经营趋势 | 统计口径、结果、解释、建议动作、数据状态 |

模板 MUST 允许业务差异。订单桌台工作台不能为了视觉统一被改造成普通 Card List，设置页也不应复制 Dashboard 结构。

### 6.4 组件治理流程

`发现重复 -> 确认业务语义一致 -> 盘点消费者 -> 定义状态合同 -> 小范围复用 -> 验证 -> 扩大使用`

禁止从“看起来相似”直接跳到全局抽象。疑似失活组件进入 Phase-04 清单，不在高频页面改造中顺手删除。

## 7. 高频页面改造路线

此处优先级表示迁移波次，不表示当前缺陷严重度。所有波次都遵守 Touch And Migrate。

### P0：OrderManage + Dashboard

#### OrderManage

目标不是增加功能，而是降低忙时决策成本：

1. 冻结新订单、同步失败、打印未知、支付与退款的状态合同；
2. 以真实工作流验证接单、出餐、结账、补打的步骤和误触风险；
3. 明确桌台视图与列表视图的 Jobs，不重复堆叠同一信息；
4. 需求触摸时再沿“当前订单、历史订单、桌台详情、订单动作”边界减小单文件；
5. 不改变订单状态机、API 或业务流程。

#### Dashboard

1. 固定首屏顺序为可行动异常、今日结果、经营解释；
2. 继续保持正常状态静默、未知状态显式；
3. 每张卡必须回答“老板看完要不要做事”；
4. 次要曝光、配置和说明不得抢占订单或异常；
5. 不因为模块多就合并 API 或删除数据，性能动作等待 Phase-05 证据。

### P1：DishManage + MemberManage

#### DishManage

先修状态真实性，再解决目标菜品可达性，然后才验证 500+ 的渲染边界。名称搜索、分页、分段或虚拟化属于不同方案，
必须由真实任务和性能数据决定，不能在本蓝图中预选实现。

#### MemberManage

先接通真实分页与全量可达，再基于老板 Jobs 组织搜索、分层、消费价值和发券动作。禁止把一次返回更多数据当作分页，
也不得在没有权限和业务规则的情况下增加批量营销。

### P2：Marketing

1. 先修自动营销、券列表和效果页的状态真实性；
2. 再建立“当前运行状态、投入、结果、建议动作”的解释链；
3. Vant 页面按触摸迁移，不做一次性 Ant 替换；
4. 不新增无法由后端真实数据证明的智能建议；
5. 不以更多营销入口代替效果闭环。

## 8. Touch And Migrate 策略

### 8.1 准入规则

- 新页面 MUST 遵守产品定位、UI 框架、页面结构、状态和性能合同；
- 修改旧页面 MUST 只迁移本次需求触摸到的任务路径和相邻状态；
- 未触摸页面 MAY 保持现状；
- 修复 P0 状态真实性时 MUST 保持业务流程、接口字段和已确认操作不变；
- 组件抽取 SHOULD 发生在第二个真实消费者出现之后；
- 每次迁移 MUST 有前后任务路径、状态矩阵和回归检查。

### 8.2 允许与不允许

| 允许 | 不允许 |
| --- | --- |
| 在被触摸页面补齐 error/unknown | 一次性替换所有空态和加载态 |
| 使用现有 Ant 组件减少重复 | 再造 Button、Card、Form 基础库 |
| 沿稳定业务边界小步拆分超大文件 | 为降低行数提前重构整个页面 |
| 清点 Vant 消费者并停止新增 | 一次性将 Vant 页面全部改为 Ant |
| 用真实数据决定性能动作 | 因 701 KB gzip 或文件行数直接优化 |
| 保留页面的业务差异 | 为视觉一致把订单工作台改成普通列表 |

### 8.3 每次触摸的最小验收

1. Job 是否更快完成；
2. loading、empty、error、success、unknown 是否正确；
3. 业务失败是否会错误显示成功；
4. 危险动作是否可识别且可确认；
5. 权限和角色路径是否保持；
6. 当前数据规模是否仍可达；
7. 是否保持已有性能事件和版本合同；
8. 是否只修改了需求范围内文件。

## 10. 当前成熟度与差距

### 10.1 成熟度结论

当前 `admin-h5` 前端系统成熟度为 **L2，64/100**：已有可靠工程底座、治理合同、部分业务组件和可观测能力，
但页面执行仍碎片化，尚未达到可持续复制的成熟 SaaS 后台水平。

架构基础单项为 74/100，高于整体产品系统成熟度。差距主要不在 Vue、Vite 或路由，而在以下方面：

1. 状态合同尚未覆盖所有高频页面和所有业务失败；
2. 页面结构没有稳定围绕老板、店长、店员的 Job 组织；
3. 菜品和会员在大规模数据下的查找与可达性不足；
4. 业务组件有成功案例，但没有完整消费者清单和准入流程；
5. 设计变量、两套 UI 框架和页面私有样式尚未形成单一治理边界；
6. 超大页面让局部修改难以隔离风险；
7. 性能已有观测能力，但没有足够 production 样本支持归因和优化。

### 10.2 下一阶段优先事项

下一阶段应进入 Phase-02，先建立最小可执行的后台页面与组件准入规格，重点冻结：

1. 业务失败与 unknown 的状态矩阵；
2. Workbench、Manage List、Detail/Edit、Effect/Insight 四类页面评审模板；
3. Ant PRIMARY、Vant LEGACY 和原生 HTML 的使用边界；
4. 组件消费者清单、复用门槛和疑似失活组件审计方法；
5. P0 页面 OrderManage、Dashboard 的 Jobs 验收清单。

在任何视觉改造之前，菜品、会员和 CouponCenter 的状态真实性问题应作为独立小步修复候选排入后续实施，
但不在本阶段修改。

## 11. 坚决不做

- MUST NOT 复制消费者端 UI、卡片节奏或转化逻辑到商家后台；
- MUST NOT 引入第三个 UI 框架；
- MUST NOT 建立与 Ant Design Vue 平行的新基础组件库；
- MUST NOT 一次性替换 Vant 或全部历史页面；
- MUST NOT 为统一外观牺牲订单、桌台、菜品等真实业务差异；
- MUST NOT 为降低文件行数发起后台大重构；
- MUST NOT 修改订单状态机、API 字段、数据库结构或权限边界；
- MUST NOT 使用空列表、0 或默认运行状态掩盖失败和未知；
- MUST NOT 根据 bundle 体积、代码感觉或 staging 数据提前做性能优化；
- MUST NOT 为达到性能样本门槛制造虚假 production 流量；
- MUST NOT 在未证明无消费者前删除历史组件；
- MUST NOT 为了统一而统一。

## 12. 最终回答

1. **当前 admin-h5 成熟度？** L2，64/100。工程架构基础为 74/100，已具备继续治理的可靠底座，但产品和设计系统尚未形成一致执行能力。
2. **距离成熟 SaaS 后台差距在哪里？** 主要是状态真实性覆盖、Jobs 驱动的信息架构、大数据可达性、组件准入、设计语言单一来源和小步维护能力，不是缺少新技术栈。
3. **未来后台前端系统应该是什么？** 一个移动优先、角色分工明确、异常和待办优先、结果可信、操作路径短、能随业务规模增长的餐饮经营工作系统。
4. **下一阶段优先改什么？** 先在 Phase-02 冻结最小可执行规则，再以 OrderManage 和 Dashboard 为 P0 页面波次；状态缺陷按严重度单独小步处理，优先菜品、会员和营销的失败真实性。
5. **哪些东西坚决不做？** 不复制消费者端、不换框架、不建平行组件库、不一次性重构、不为视觉统一牺牲业务、不凭猜测优化性能。
