本文只审计当前事实，不修改业务代码、组件、接口或数据库。结论来自源码静态扫描、现有治理文档和一次真实生产构建。由于本阶段没有可用的商家登录态、生产接口样本和真机测试环境，本文不声称完成真实设备可用性测试，也不虚构 API P50/P95 或白屏时长。

审计判断顺序统一为：

> 已存在能力 → 设计债务 → 影响商家体验的问题 → 建议执行顺序

## 1. 当前技术和设计现状

### 1.1 技术基线

| 项目 | 当前事实 | 判断 |
|---|---|---|
| 前端框架 | Vue 3.4 + Vite 5.4，39 个 view、19 个本地 Vue 组件 | 技术栈稳定 |
| 主 UI 框架 | Ant Design Vue 4.2.6，全局 `app.use(Antd)` | 应继续作为后台主框架 |
| 第二 UI 框架 | Vant 4.8.1，全局 `app.use(Vant)` | 已形成历史双轨，不应继续扩散 |
| 状态管理 | Pinia 已接入，当前只有 `stores/auth.js`；订单同步走 composable，页面业务态以本地 `ref/reactive` 为主 | 基础合理，但跨页治理弱 |
| 路由 | 业务页全部动态导入 | 页面级拆包已建立 |
| 请求 | Axios 单实例、10 秒超时、JWT、401/403处理、轮询去重、开发态耗时日志 | 基础能力较完整 |
| 移动端 | 底部 TabBar、安全区、底部 Drawer、卡片列表 | 移动端方向明确 |
| 暗色 | Ant 跟随系统暗色，CSS token 也会翻转 | 只完成半套，存在混色风险 |

### 1.2 现有治理资料

已存在能力：

- `docs/frontend/DESIGN_SYSTEM_CURRENT.md` 已完成两端视觉现状反向审计。
- `member-mini-client/docs/frontend/FRONTEND_CONSTITUTION.md` 已为消费者端建立可执行的结构合同。
- `admin-h5/src/styles/global.scss` 有品牌、文本、背景、边框、圆角、状态色和阴影变量。
- `admin-h5/src/App.vue` 有 Ant Design 主题配置。
- Obsidian 前端规范已把 `MenuManage.vue`、`OrderManage.vue` 标为优先拆分对象。

设计债务：

- 没有一份只面向 `admin-h5` 的设计标准或可执行前端 Constitution。
- 现有 `DESIGN_SYSTEM_CURRENT.md` 是事实审计，不是新页面的准入规范。
- “后台优先用哪个框架、哪些控件允许自写、状态页怎么做、列表何时分页、点击热区多大”没有统一合同。

商家影响：

- 新页面能继续沿用任何一套历史做法，视觉和交互会随开发者选择漂移。
- 同一商家在“今日、接单、菜单、营销、设置”之间切换时，需要重新理解页面语言。

建议顺序：

1. 先冻结当前事实和例外，不改页面。
2. 下一阶段只写 `admin-h5` 独立标准，明确 Ant Design Vue 为主框架、Vant 为 legacy。
3. 后续按高频页面被触摸时迁移，禁止一次性重做。

### 1.3 当前商家后台设计评分

**总分：63 / 100。成熟度：B，部分存在。**

| 维度 | 得分 | 主要理由 |
|---|---:|---|
| 设计治理 | 12 / 20 | 有 token、主题和现状审计，没有后台独立标准 |
| 组件一致性 | 9 / 15 | Ant 是事实主框架，但 Vant、原生控件和本地组件三轨并行 |
| 高频任务体验 | 22 / 30 | 接单链路较强，首页、打印、单品上下架和营销理解仍有断点 |
| 性能与大数据量 | 10 / 20 | 路由懒加载、订单增量同步较好；首屏共享包、会员和菜品大数据量有明显风险 |
| 工程可维护性 | 10 / 15 | 请求层、轮询和部分 composable 较好；超大文件、死组件、响应解包分散 |

这个分数不是“视觉好不好看”的主观分，而是老板能否快速完成任务、系统能否在弱网和大数据量下保持确定性、团队能否持续小步演进的综合分。

## 2. 设计体系成熟度

### 2.1 成熟度矩阵

分类口径：A 已建立，B 部分存在，C 缺失。

| 项目 | 等级 | 已存在能力 | 主要缺口 |
|---|---|---|---|
| Design System | C | 有反向审计和局部事实标准 | 没有后台独立设计合同、组件准入和治理流程 |
| Theme | B | `a-config-provider` 定义品牌绿、语义色、圆角、字体和明暗算法 | 自写 CSS、Vant 和硬编码色没有完全跟随主题 |
| Token | B | `global.scss` 有语义 CSS 变量，`variables.scss` 有 SCSS 档位 | 两套 token 并存，旧 SCSS 仍是 indigo |
| CSS 变量 | A | `--brand`、`--text-*`、`--bg-*`、`--border` 等已被大量使用 | 覆盖范围仍不完整 |
| 色彩规范 | B | 品牌绿、文本三级、成功/危险/警告色已形成 | 695 次硬编码 hex 静态出现；营销页有多组紫、蓝、橙、金局部色 |
| 字体规范 | C | 有统一系统字体栈 | 没有字号、行高、数字、标题/正文角色合同 |
| 间距规范 | B | SCSS 有 4/8/12/16/24px，页面常见 12/16px 节奏 | 页面很少实际引用 SCSS spacing token，大量 inline style |
| 圆角规范 | B | Ant 8px、卡片 token 12px、常用胶囊形态 | 实际还有 10/14/18/28px 等多套局部半径 |
| 阴影规范 | B | 有 `--card-shadow` | 多个页面自行写阴影，暗色适配不完整 |
| 状态色 | B | 全局订单状态 tag 和 Ant 语义色存在 | 页面仍有大量局部状态色，命名和含义不总一致 |
| 暗色规范 | B | Ant 和 CSS token 会跟随系统 | Layout、PageHeader、TabBar、Vant 默认样式有硬编码浅色，可能出现半暗半亮 |
| 动效规范 | B | 有 `animate-in`、`tap-shrink`、`prefers-reduced-motion` | 仍有页面局部动效，缺少“只为反馈和状态变化服务”的后台标准 |

### 2.2 Token 权威冲突

已存在能力：运行时品牌权威基本是 `--brand: #07C160`，Ant `colorPrimary` 同值。

设计债务：

- `styles/variables.scss` 仍把 `$color-primary`、`$primary-main` 定义为 `#6366f1`，且通过 Vite `additionalData` 全局注入。
- `DataCard.vue` 仍消费旧 indigo 渐变，虽然当前无页面引用。
- 静态扫描得到约 996 次 `var(--*)` 使用，同时仍有约 695 次 hex 出现。该数量包含局部业务色和变量定义，只能说明“硬编码仍很普遍”，不能等同于 695 个缺陷。

商家影响：新功能若误用旧 SCSS 变量，会在绿色后台中突然出现第二品牌色。暗色模式下硬编码白底/黑字也会造成局部不可读。

建议顺序：先确定 `global.scss + Ant theme` 为运行时权威，再冻结旧 SCSS 色源。不要做全量 hex 替换，业务状态色和优惠券色应保留语义。

### 2.3 UI 框架和自定义组件

静态扫描范围为 58 个 view/component Vue 文件：

| 使用方式 | 文件数 | 结论 |
|---|---:|---|
| 出现 Ant `<a-*>` | 30 | 主框架事实明确 |
| 出现 Vant `<van-*>` | 16 | 第二套框架覆盖仍广 |
| 同一文件同时使用 Ant 和 Vant | 1 | Dashboard 直接混用 |
| 出现原生 `<button>` | 27 | 本地交互样式大量存在 |
| `<style scoped>` | 55 | 页面局部样式是主流 |

组件一致性：

| 类型 | 当前实现 | 一致性问题 |
|---|---|---|
| Button | Ant Button、Vant Button、原生 button | 高度、圆角、loading、disabled、按压反馈不一致；头部按钮常只有 28px |
| Card | Ant Card、`section.panel-card`、`.hero-card`、`.customer-card` 等 | 卡片语义和圆角由页面决定 |
| Table | 实际只有约 1 个文件使用 table 类组件，多数数据页用卡片或 CSS grid | 不是缺 Table 组件，而是缺少“移动端何时用卡片、何时可横向表格”的规则 |
| Form | 设置/菜单以 Ant Form 为主，营销/消费以 Vant Field 为主，部分原生 input | 校验和错误位置不同 |
| Modal / Drawer | 9 个文件使用 Ant Modal/Drawer；5 个使用 Vant Popup/Dialog | 底部抽屉高度、关闭方式、footer 和安全区不一致 |
| PageHeader | 19 个页面使用 `PageHeader`；Menu/Order/More 自写 `.page-header`；Dashboard 使用 Hero | 三类页头并存 |
| Empty | Ant Empty、Vant Empty、本地文案块、死代码 ListState | 加载失败与空数据有时混为一谈 |
| Loading | Ant Skeleton、Vant Loading、局部 loading 文案 | 同一后台的等待反馈力度不一致 |

### 2.4 组件复用现状

已存在能力：

- `PageHeader.vue` 被 19 个页面复用，是最成熟的后台页面原语。
- `WorkbenchSyncBar`、`AssistedOrderSheet`、`PickupNoPicker` 已围绕岗位工作台复用。
- Dashboard 已拆出 `StatCard`、`InsightCard`、`RankList`、`TrendChart`。

设计债务：19 个本地组件中有 9 个没有任何 view/component 引用：

- `CustomCheckbox.vue`
- `CustomDatePicker.vue`
- `CustomRadio.vue`
- `CustomTable.vue`
- `DataCard.vue`
- `ListState.vue`
- `NavBar.vue`
- `PaginationBar.vue`
- `RefreshList.vue`

其中 `ListState.vue` 使用未安装的 Element Plus 标签，`DataCard.vue` 使用旧 indigo 色源。这些文件不是“可复用资产”，而是会误导后续开发的伪标准。

建议顺序：下一阶段先标记 authority 和 legacy，不急着删。只有在确认无动态引用、无历史依赖后，单独开清理任务。

## 3. 页面体验问题

### 3.1 首页 / 工作台

已存在能力：

- 第一眼能看到日期、门店名和营业状态。
- 待接单、待结账、打印异常会生成可点击待办。
- 新订单在底部“接单”Tab 有角标，Dashboard 每 30 秒同步订单。
- 今日营收、订单数、客单价、新会员、会员总数、趋势和热销榜已有结构化展示。
- 统计卡有骨架、错误重试和更新时间。

设计债务：

1. 模板顺序是 Hero → 套餐状态条 → 待办 → 今日战报。代码注释说套餐不能挡在订单/KPI 之前，但实际仍位于待办之前。
2. 首页首次挂载并发/并行触发 7 类请求：门店资料、Dashboard 统计、今日订单、系统状态、营销预览、异常桌、套餐。
3. 营销、异常桌、套餐和门店资料失败多为静默，页面没有统一“部分数据未更新”状态。
4. 首屏继续向下堆叠会员、趋势、转化、营销、热销榜，新订单虽明显，但一屏内经营信息过长。
5. 营业状态点击后乐观更新，失败会回滚并提示，这部分是正例，应保留。

商家影响：

- 忙时老板最关心“有没有新订单、是否要结账、打印是否正常”，套餐信息不应先于这三类动作。
- 多卡片长页面适合复盘，不适合饭点时快速扫一眼。
- 部分请求静默失败时，老板无法区分“今天为 0”和“这块数据没拉到”。

建议顺序：

1. P0 保留待办和 Tab 角标为订单 authority，明确饭点模式优先级。
2. P1 再评估把套餐移到经营数据之后，并压缩首屏为“待办 + 今日核心结果”。
3. 不重画 Dashboard，不新增数据中台。

### 3.2 订单管理

已存在能力：

- 当前/历史、桌台/列表、状态筛选、桌号/尾号/菜名搜索路径清楚。
- 接单、拒单、出餐、确认上菜、结账、退款、补打都有明确 loading 和结果反馈。
- 支付状态、来源、桌牌、打印失败、退款关注等关键事实可见。
- 支持桌级“全部接单/全部出餐”，高频批量操作路径短。
- 历史订单后端分页，每页 20；当前订单显示先切 20 条，订单同步已有 full snapshot + delta cursor。
- 网络连续失败 3 次后有警告和重试。

设计债务：

1. `OrderManage.vue` 已达 1933 行，页面、同步、映射、筛选、桌台聚合、支付、退款、打印、代客加单全部集中。
2. 顶部同时放“代客加单、提醒状态、刷新”，按钮高度约 28px，小屏点击热区偏小。
3. 当前/历史和桌台/列表形成两层 Tabs，状态筛选再形成第三层，信息密度高但导航层级重。
4. 正常订单没有显式“打印/再次打印”入口；只有 `failed/unknown` 状态显示“补打小票”。结账账单 Modal 也没有打印动作。是否允许正常补打需要产品确认，不能直接增加按钮。
5. 当前订单初始快照仍加载当天及未完结订单全集，前端只是在列表层 slice 20。极端单日 1000+ 时，映射、桌台聚合和内存仍吃全量数据。
6. Dashboard 和 TabBar 也会独立读取订单，虽然有 dedupe/polling manager，仍存在多个消费者维护相似统计口径。

商家影响：

- 日常接单路径已经较强，最大风险不是“按钮不好看”，而是忙时误触、三层筛选认知负担和极端订单量性能。
- 正常重打如果是门店常见动作，当前只能等异常状态或走设备流程，操作路径不确定。
- 超大文件使任何订单 UI 小改都容易碰到支付、桌台会话、打印和退款合同。

建议顺序：

1. P0 先用真实门店确认“正常补打”的业务权限和审计要求，不先加按钮。
2. P0 对 1000+ 当日订单做数据和渲染压测，判断 full snapshot 是否需要有界化。
3. P1 在不改状态机的前提下，按“同步数据、桌台派生、订单动作、代客加单 UI”小步拆分。

### 3.3 菜品管理

已存在能力：

- 添加菜品入口明确，支持菜品库导入和 AI 文本导入。
- 编辑抽屉可以修改名称、图片、价格、分类、上下架、库存、规格和排序。
- 售罄/恢复在列表外层一键完成。
- 分类支持批量上架/下架，保存和失败均有反馈。
- 表单先展示顾客端预览，高级字段默认折叠，符合老板“先完成核心字段”的习惯。
- 删除放在“更多”菜单并二次确认，降低忙时误删风险。

设计债务：

1. 顶部 3 个动作在窄屏并列，且都使用 small 按钮，主次不够稳定。
2. 单个菜品“售罄/恢复”是一键操作，但单品“下架/上架”需要进入编辑抽屉；老板可能混淆“售罄”和“下架”。
3. 没有菜品名称搜索。500+ 菜品时只能按分类滚动。
4. `GET /v1/menu/items` 对商家返回全部菜品和完整规格，后端无分页；前端按分类全量渲染，无虚拟化。
5. `dishesByCategory(cat)` 每次对全量数组 filter，类别列表、数量和渲染会重复扫描。
6. `loadMenu()` 失败时直接把 `allDishes=[]`，随后展示“还没有菜品”。网络失败会被误报为门店空菜单。
7. `MenuManage.vue` 已达 1527 行，列表、编辑、图片、分类、规格、AI、菜品库集中在一个文件。

商家影响：

- 500+ 菜品时定位和修改价格的成本明显上升。
- 弱网下把加载失败显示成“没有菜品”，会让老板误以为菜单被清空，这是比视觉不一致更严重的确定性问题。
- “售罄”和“下架”缺少稳定语义，容易造成顾客端是否可见的误判。

建议顺序：

1. P0 先把加载失败与空菜单分开，这是状态正确性，不是重设计。
2. P0 设计 500 菜品基准和搜索/分页策略，后端若新增可选分页参数必须保持旧响应兼容。
3. P1 再收敛“售罄/下架”的命名与说明；不应为了统一把二者合并成同一业务状态。

### 3.4 会员与营销

已存在能力：

- 会员列表支持搜索、状态、发券、停用/恢复和详情。
- 会员详情集中展示积分、累计消费、优惠券、消费记录和操作记录。
- 优惠券中心用“保守/标准/激进”降低参数学习成本，高级设置默认折叠。
- 营销效果按 7/30/90 天展示发券、核销率、GMV 和裂变人数。

设计债务：

1. 会员列表固定请求 `page_size=100`，之后“加载更多”只是前端 slice。会员 10000+ 时，第 101 位之后永远不可见。
2. 列表模板尝试显示 `store_member_no`，映射对象却没有保留该字段，会员卡号不会出现。
3. 优惠券中心完全使用 Vant，会员列表和详情使用 Ant，营销效果又混合 PageHeader + Vant 状态组件，像三套产品。
4. 自动营销 Hero 固定写“自动运行中/已为你开启”，加载失败时仍可能呈现默认运行状态。
5. “绝不会让你亏本”属于无法由当前 UI 证明的绝对承诺，容易让商家误解算法风险。
6. 会员、消费记录、优惠券记录分别使用不同的分页/数据提取方式，响应层兼容逻辑分散。

商家影响：

- 大会员库下的核心问题不是慢，而是数据不可达，会直接影响查人、发券和停用。
- 自动营销状态如果加载失败仍显示为运行中，会让老板对实际发券状态产生错误信心。
- 积分、优惠券、消费和营销指标虽都有页面，但概念解释和框架外观不统一，学习成本偏高。

建议顺序：

1. P0 修正会员真实服务端分页/搜索可达性。
2. P0 让营销运行状态以接口事实为准，加载失败显示不确定状态。
3. P1 统一概念文案和状态反馈，暂不重画券面或会员卡。

### 3.5 设置类页面

已存在能力：

- 设置首页按“常用设置/其它工具”分组，有未配置标签和摘要。
- 经营、支付、设备、通知、套餐拆成独立二级页。
- 表单普遍有 loading、保存成功/失败反馈，高风险密钥重置有确认。
- 经营设置先展示“顾客现在看到”的结果，有利于老板理解配置后果。

设计债务：

1. `StoreSettings` 同时包含门店资料和数字桌牌；`DeviceSettings` 又包含打印机、排位、收银 API、碰一碰，边界不够稳定。
2. 设备页一次加载门店、打印机、POS、领券页、企微联系人，多块失败最终可能只显示一个泛化 toast。
3. 多个 switch 在 `@change` 时立即保存，失败后缺少统一回滚策略；用户可能以为开关已生效。
4. `PageHeader` 和 Layout/TabBar 使用硬编码白底/黑字，跟随系统暗色时可能与页面 token 不一致。
5. 部分设置文案偏技术，例如 appId、appSecret、shareCode、SN、API Key，缺少“在哪里找/改错会怎样”的渐进说明。

商家影响：

- 老板按“我想配桌牌/打印/收银”找入口时，需要理解系统内部分类。
- 即时保存失败却没有可靠回滚，会降低对设置状态的信任。
- 设备页技术字段密集，适合实施人员，不完全适合普通餐饮老板自助完成。

建议顺序：先保证保存状态确定性和错误定位，再调整分组文案。不要把所有设置重新合并成一个大表单。

## 4. 性能问题

### 4.1 首屏加载与包体

生产构建命令：`npm run build`，结果成功，3683 个模块完成转换。

路由懒加载已存在，但 `main.js` 全局注册 Ant 和 Vant，构建后的 `index.html` 会预加载全部共享 vendor：

| 首屏共享资源 | 原始体积 | gzip |
|---|---:|---:|
| 主入口 JS | 26.59 KB | 8.77 KB |
| Vue/Router/Pinia | 109.46 KB | 42.70 KB |
| Ant Design Vue | 1291.58 KB | 381.45 KB |
| Vant | 220.20 KB | 78.33 KB |
| 其它 vendor | 361.40 KB | 127.59 KB |
| 首屏共享 JS 合计 | **约 2.01 MB** | **约 638.84 KB** |
| 首屏共享 CSS 合计 | **约 283.38 KB** | **约 62.53 KB** |
| JS + CSS 合计 | **约 2.29 MB** | **约 701.37 KB** |

最大业务路由 chunk：

| 页面 | JS 原始 | gzip |
|---|---:|---:|
| OrderManage | 49.53 KB | 15.03 KB |
| MenuManage | 38.34 KB | 12.50 KB |
| Dashboard | 17.53 KB | 7.41 KB |

判断：页面级拆包是 A 已建立能力，但全局 UI 框架注册抵消了首屏收益。弱网或旧手机首次打开时，约 701 KB gzip 的共享资源会直接推高白屏和可交互时间。当前没有 admin-h5 的 LCP、INP、白屏或路由切换生产指标，因此不能给出真实毫秒结论。

### 4.2 接口响应能力

已存在能力：

- 后端所有响应提供 `X-Process-Time-Ms`。
- `SLOW_REQUEST_MS=100`，超过 100ms 会写 WARNING。
- Dashboard 统计接口缓存 60 秒。
- 前端请求记录开发态 duration，轮询有 dedupe、页面隐藏/闲置降频。
- 订单 full + delta cursor 能减少持续轮询的全量传输。

设计债务：

- admin-h5 不采集生产侧接口 P50/P95/P99，也不记录首屏和路由可交互指标。
- Axios 只在 DEV 输出 duration，线上无法从前端区分后端、网络和渲染。
- Dashboard 一次进入触发 7 类请求，首屏信息被多接口成功与否切碎。
- 请求层没有统一业务错误归一化，页面反复检查 `res.code`、`res.success` 和多层 `data`。

结论：后端具备性能观测基础，但本阶段没有可证明的“首页/订单/列表接口响应达标”数据。下一阶段应先采样，再优化 SQL 或接口，禁止凭包体或源码猜测数据库慢。

### 4.3 大数据量

| 场景 | 当前能力 | 风险等级 | 结论 |
|---|---|---|---|
| 订单 1000+ | 历史订单服务端分页 20；当前订单 delta 同步；列表只显示前 20 | 中高 | 当前快照、聚合和桌台视图仍处理全量，需压测 |
| 菜品 500+ | 全量接口、分类筛选 | 高 | 无搜索、分页、虚拟化，DOM 和计算随全量增长 |
| 会员 10000+ | 后端支持分页/搜索 | P0 高 | 前端只取前 100，属于数据不可达，不只是性能问题 |
| 券/记录 | 多数请求 page_size 100 或自行 extractRows | 中 | 分页合同不统一，极端量下行为不确定 |

### 4.4 错误、加载和保存反馈

已存在能力：订单、会员列表、营销效果、订阅等核心页已有 loading/error/empty；大多数保存动作有 loading 和 toast。

主要问题：

- Menu 加载失败被转换为空菜单。
- Dashboard 多个次要接口静默失败，没有“部分数据未更新”。
- 代码中存在 15 处空 catch，部分是可接受的非关键 best-effort，部分会掩盖数据状态。
- 全局只统一处理 401/403，5xx、超时、离线、业务 `code != 200` 由页面各自决定。
- 暗色模式和混合框架使 loading/empty/error 视觉不稳定。

## 5. 工程问题

### 5.1 单文件规模

`admin-h5/src` 中有 17 个 `.vue/.js` 文件超过 500 行，3 个超过 800 行。

| 文件 | 行数 | 风险 |
|---|---:|---|
| `views/OrderManage.vue` | 1933 | 状态机、同步、页面和多业务动作耦合 |
| `views/MenuManage.vue` | 1527 | 列表、表单、图片、分类、规格、AI/菜品库耦合 |
| `views/StaffReferral.vue` | 865 | 业务和页面集中 |
| `views/OrderPage.vue` | 799 | 下单链路集中 |
| `views/Distribution.vue` | 791 | 配置、列表和结算集中 |
| `views/ChannelEntryList.vue` | 736 | 入口、券、海报等集中 |
| `views/H5Order.vue` | 675 | H5 点单业务集中 |
| `views/SuperAdmin.vue` | 666 | 平台能力集中 |
| `settings/SubscriptionSettings.vue` | 658 | 套餐、支付、轮询、人工付款集中 |
| `components/AssistedOrderSheet.vue` | 656 | 代客点单弹层过重 |

影响：大文件本身不会直接让老板觉得慢，但会让任何小改都更难验证，尤其 OrderManage 同时承载支付、退款、桌台、打印和订单同步合同。

建议：只在下一次真实需求触摸对应模块时拆，先拆纯派生和独立业务块，不重构整个项目。

### 5.2 状态管理

判断：**不是“全面混乱”，而是“局部合理、跨页弱治理”。**

已存在能力：

- 登录/权限进入 Pinia `auth` store。
- 订单同步已抽为 `useWorkbenchSync` 和 core。
- 轮询集中到 `pollingManager`。

设计债务：

- 其它跨页事实仍散在 localStorage、页面本地 ref、API 重拉和重复映射中。
- Dashboard、TabBar、OrderManage 都消费订单并各自派生部分统计。
- Pinia 已存在，但不应为了“看起来统一”把所有页面状态迁进去。

建议：只有确实跨页共享、需要单一 authority 的状态才进入 store。页面表单、筛选、Drawer 开关继续保持本地。

### 5.3 接口调用规范

已存在能力：API 函数集中在 `src/api/index.js`，Axios origin、token、timeout、ID 字符串化和轮询去重统一。

设计债务：

1. 运行时主要响应是 `{ code, msg, data }`，queue API 使用 `{ success, message, data }`，与当前全局要求的 `{ success, message, data }` 不一致。
2. 前端存在约 87 处 `res?.data?.data || res?.data`、`extractRows`、`rowsFrom` 等兼容提取痕迹。
3. 同一业务错误可能从 HTTP 状态、`code`、`success` 或嵌套 `message/msg` 进入页面。
4. 当前不应直接改 API 字段。应在兼容边界归一化，等后续单独 API 治理阶段再决定正式合同。

商家影响：接口返回层级漂移时，页面容易把错误当空数据，最典型就是菜单和营销状态。

### 5.4 自动化检查

已存在能力：`npm run check` 包含文本编码、多个业务契约脚本和生产构建。

设计债务：共有 25 个 `test-*.mjs`，其中以下 5 个未接入 package scripts / `npm run check`：

- `test-dashboard-actionable-state.mjs`
- `test-order-manage-session-isolation.mjs`
- `test-p0-09-money-safety.mjs`
- `test-p0-refund-exposure.mjs`
- `test-p1-02-historical-orders.mjs`

影响：这些文件存在不代表默认门禁会执行。订单/退款/首页行为可能出现“有测试但 CI 未跑”的假安全感。

## 6. 商家后台设计原则

以下原则只适用于 SaaS 商家后台，不直接套消费者端小程序。

### 6.1 效率优先，但不牺牲资金和状态确定性

- 高频动作一到两步完成：接单、出餐、售罄、恢复、结账。
- 退款、删除、重置密钥等高风险动作必须确认并留下明确结果。
- “更少点击”不能绕过支付、桌台会话、打印审计和权限合同。

### 6.2 信息优先，按“现在要做什么”排序

首页先显示待接单、待结账、打印异常，再显示经营复盘和套餐信息。

订单卡先显示状态、桌号、时间、菜品和主动作。营销卡先显示是否运行、实际效果和成本，再解释算法。

### 6.3 状态必须明确，不用颜色代替文字

- 每个订单、支付、打印、退款、保存动作都必须有文字状态。
- loading、empty、error 必须是三种不同事实。
- 自动保存失败必须回滚或明确显示“未保存”。

### 6.4 操作路径最短，但主次只能有一个

- 同一区域只保留一个最高优先级动作。
- 次要导入、设置、复制等进入次级入口，不与“接单/加菜/保存”并列抢注意力。
- 小按钮不能因为放在 header 就缩到难点，移动端触控热区应优先保证。

### 6.5 为饭点和弱网设计

- 接单页不能因为统计、营销或套餐接口失败而不可用。
- 首屏先给可操作状态，复盘数据可以后到。
- 离线、超时、数据过期必须能被老板理解，不显示虚假的 0 或空列表。

### 6.6 信息密度服务任务，不追求“像小程序”

- 商家后台允许更高密度，但密度要来自对齐、分组和稳定字段，不靠缩小字号和点击区。
- 桌台和订单在手机上适合卡片；只有真正需要横向比较的数据才使用表格。
- 不把消费者端的大 Hero、券面、强转化 CTA 机械复制到所有后台页面。

### 6.7 低学习成本来自业务语言

- 使用餐饮老板熟悉的“接单、出餐、售罄、下架、结账、补打”。
- 技术字段必须解释来源和后果。
- “售罄”和“下架”保持不同业务含义，但 UI 要解释区别。

### 6.8 渐进治理，不为了统一而统一

- Ant Design Vue 继续作为主框架，不引入第三个 UI 框架。
- Vant 稳定旧页面可暂留，新页面不再扩散。
- 不为每个 Ant Button/Card 再包一层 AppButton/AppCard。
- 只有重复的业务语义和交互合同才值得成为组件。
- 旧页面按 TOUCH_AND_MIGRATE，小步迁移，不做后台大改版。

## 7. 优先级排序

### 7.1 当前最大问题 TOP10

| 排名 | 问题 | 级别 | 对商家的直接影响 |
|---:|---|---|---|
| 1 | 会员列表只取前 100 条，后续会员不可达 | P0 | 10000+ 会员时查不到人、无法发券或管理 |
| 2 | 菜单加载失败被显示成“没有菜品” | P0 | 老板可能误以为菜单被清空 |
| 3 | 首屏同时预加载 Ant + Vant，共享 JS/CSS 约 701 KB gzip | P0 | 弱网首次打开白屏和可交互延迟 |
| 4 | 菜品 500+ 无搜索/分页/虚拟化，全量接口和渲染 | P0 | 修改价格、图片、上下架越来越慢 |
| 5 | 后台没有独立设计/交互/性能准入标准 | P0 | 新页面继续产生第四套实现 |
| 6 | API 响应形态双轨，前端有约 87 处兼容解包 | P1 | 错误容易被当空数据，状态不可信 |
| 7 | OrderManage 1933 行、MenuManage 1527 行 | P1 | 高频业务小改回归风险高 |
| 8 | Ant/Vant/原生控件三轨，9 个本地组件无引用 | P1 | 页面学习成本高，开发容易选错标准 |
| 9 | 首页套餐位于待办前，且进入页触发 7 类请求 | P1 | 饭点时行动信息不够纯粹，部分数据状态碎片化 |
| 10 | 暗色只完成半套，PageHeader/Layout/TabBar/Vant 仍硬编码浅色 | P2 | 系统深色用户可能看到混色和低对比界面 |

### 7.2 优先级判断规则

- P0：数据不可达、状态错误、首屏成本、高频任务阻塞、后续治理入口。
- P1：跨页面一致性、可维护性、交互理解成本。
- P2：长期视觉清理、暗色完整性、死代码和细节可访问性。

不把“所有圆角不一样”定为 P0，也不把“统一成一个组件”本身当目标。

## 8. 下一阶段执行方案

### 8.1 P0 路线：先确保能快、能找、状态可信

建议拆成独立小阶段，禁止合并为一次大改：

1. **P0-A 性能基线**
   - 记录 admin 首屏 JS/CSS、LCP/INP、路由可交互和核心 API client/server/network 分段。
   - 验收必须包含冷启动、弱网和旧手机，不以本地构建时间代替。

2. **P0-B UI 框架加载治理**
   - 目标是避免首屏全量预加载两个 UI 框架。
   - 不引入新框架，不要求一次迁完 Vant 页面。
   - 先验证登录、Dashboard、OrderManage 的首屏资源变化。

3. **P0-C 会员大列表正确性**
   - 使用后端现有分页与搜索能力，保证第 101 位以后可达。
   - 不改字段、不改数据库、不一次加载 10000 条。

4. **P0-D 菜品失败态与 500+ 基准**
   - 先分开 loading/error/empty。
   - 再决定搜索、服务端可选分页或窗口渲染；接口变化必须向后兼容。

5. **P0-E 后台最小治理标准**
   - 写明 Ant 为主、Vant legacy、原生控件例外、页面状态、触控热区、移动数据表、性能预算。
   - 这是准入规则，不是建立一整套新组件库。

### 8.2 P1 路线：高频任务体验和工程小步治理

1. Dashboard 调整信息优先级，待办先于套餐，首屏只保留行动和核心结果。
2. 用真实商家访谈确认正常补打、改单、批量上下架的频率，再决定入口。
3. 收敛售罄/下架文案和操作反馈，不合并业务状态。
4. 统一响应适配边界，页面停止新增多层 `data` 猜测。
5. 按触摸模块拆 OrderManage/MenuManage，优先提取纯逻辑和已独立的业务块。
6. 把 5 个未进入默认门禁的契约脚本接入明确的 test/check 流程。
7. 设置页优先修保存回滚和错误定位，再讨论信息架构。

### 8.3 P2 路线：视觉和维护债务

1. 完成暗色模式审计，或明确后台暂不支持自动暗色。不能继续半支持。
2. 在确认无引用后清理 9 个死组件和旧 indigo 色源。
3. 按被触摸页面逐步统一 PageHeader、empty/loading/error、圆角和 spacing。
4. 补充键盘焦点、对比度、触控热区和屏幕阅读器标签检查。
5. 建立月度包体、路由 chunk 和大列表回归报告，不把一次构建结果当永久结论。

### 8.4 明确不做

- 不引入新的 UI 框架。
- 不重构整个后台。
- 不把消费者端 Frontend Constitution 原样复制给商家端。
- 不一次性替换全部 Vant、全部颜色或全部按钮。
- 不为了“统一”把移动卡片强制改成 PC 表格。
- 不修改现有数据库结构或 API 字段。
- 不在没有真实指标前优化 SQL、缓存或图片管线。
