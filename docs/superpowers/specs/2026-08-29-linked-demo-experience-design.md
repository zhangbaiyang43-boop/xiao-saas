# 开心点单双端联动演示场次设计

日期：2026-08-29

状态：待用户复核

## 1. 目标

让餐饮老板通过一次30分钟的临时演示，完整看到真实链路：顾客在微信小程序扫码点餐，订单进入商家Demo工作台，老板在手机上完成接单、制作、出餐。

该能力用于线下销售和500张体验卡，不接触真实商户数据，不发生真实支付、退款或打印。

## 2. Jobs 陈述

- 页面：商家Demo工作台
- 主要用户：餐饮老板
- 次要用户：现场销售人员
- 任务：老板在评估开心点单时，亲自确认顾客下单后商家端是否能及时看到并处理订单。
- 成功标准：顾客提交订单后2秒内出现在Demo工作台；老板可以按合法顺序完成接单、制作完成、确认上菜；每一步都有明确结果。
- 核心动作：开始体验、接单、制作完成、确认上菜。
- 禁止展示：真实商户数据、真实支付入口、退款、结账、会员导出、门店配置、员工管理、营销配置、真实打印和与本次演示无关的经营报表。

## 3. 方案决策

采用“专用演示门店 + 演示桌位池 + 临时场次令牌”。

体验卡上的商家二维码进入固定Demo启动页。启动页向后端申请一场30分钟体验，后端从演示桌位池中分配一张空闲桌，建立真实的 `DiningSession`，签发仅限该场次使用的Demo令牌，并返回这张桌对应的微信小程序码。

老板保留商家Demo工作台，销售人员或另一台手机扫描页面上的顾客点餐码。顾客端继续使用现有小程序菜单、购物车、提交订单和桌台会话能力。商家Demo工作台只显示Demo令牌中 `diningSessionId` 对应的订单。

不采用固定双二维码直接共用同一桌，因为500张物料被多人同时使用时会串单。不采用纯前端模拟，因为无法证明真实端到端能力。

## 4. 用户流程

1. 老板扫描体验卡上的“老板体验后台”二维码。
2. H5打开 `/demo`，显示“正在准备本次体验”。
3. H5用体验卡携带的启动凭证请求创建临时场次。
4. 后端验证启动凭证和频率限制，从演示桌位池中锁定一张空闲桌。
5. 后端建立或复用该桌本次唯一的开放桌台会话，签发30分钟Demo令牌。
6. H5展示倒计时、桌号和该桌已有的微信小程序码。
7. 销售人员或另一台手机扫描顾客点餐码，进入现有小程序菜单。
8. 顾客端按现有流程选菜并提交订单。演示门店采用后付模式，不唤起微信支付。
9. Demo工作台每2秒获取一次本场次订单快照，新订单出现后突出显示。
10. 老板依次操作“接单”“制作完成”“确认上菜”。
11. H5展示状态变化；顾客端现有订单状态同步机制展示对应进度。
12. 30分钟到期后，Demo令牌失效，工作台停止操作并提示重新开始体验。

## 5. 系统边界

### 5.1 复用的现有能力

- `member-mini-client` 的入口码解析、菜单、购物车、订单提交和桌台会话。
- `saas-base` 的 `DiningSession`、订单创建、订单合法状态迁移和上菜记录。
- `admin-h5` 的移动端技术栈、Ant Design Vue、请求状态表达和订单展示语言。
- 现有演示数据填充能力用于演示门店菜单初始化。

### 5.2 新增能力

- 后端Demo场次服务和Demo专属API。
- JWT类型 `demo_merchant`，只允许访问 `/api/v1/demo/*`。
- 商家后台公开路由 `/demo`，使用独立的 `sessionStorage` 保存Demo令牌。
- 独立Demo请求客户端，不读取或覆盖正式商家 `localStorage` 登录态。
- 体验卡主二维码改为Demo启动地址。

### 5.3 明确不做

- 不修改数据库结构或Alembic迁移。
- 不修改现有API字段和正式商家鉴权行为。
- 不让Demo令牌访问现有商家后台API。
- 不创建真实支付、退款、优惠券、积分、佣金或会员资产。
- 不触发真实打印机。
- 不重构现有 `OrderManage.vue`、`FrontdeskWorkbench.vue` 或小程序点餐页。

## 6. 演示门店与桌位池

生产环境配置一个专用演示租户，通过环境变量 `DEMO_TENANT_ID` 指定。该租户必须满足：

- 状态启用。
- 收款模式为 `postpay`。
- 已有可演示菜品。
- 未配置任何真实打印机或打印服务商。
- 不配置自动发券、积分、佣金和真实会员运营能力。
- 预先建立20张演示桌的有效入口码，桌号为 `DEMO-01` 至 `DEMO-20`。

每次启动场次时，后端在事务内锁定候选入口码，选择当前没有30分钟内开放场次的桌位。超过30分钟的旧演示会话先标记为过期，再分配新会话。20张桌全部占用时返回明确的“当前体验人数较多，请稍后重试”，不挤占或复用进行中的会话。

桌位池数量通过环境配置扩容，不依赖数据库结构变化。

## 7. 鉴权与安全

### 7.1 启动凭证

体验卡二维码携带有效期365天、用途为 `demo_launch` 的签名 `launchCode`。它只证明“允许申请一场Demo”，不能读取订单或调用状态操作。后端验证签名、用途和环境，不接受任意租户或桌号参数。

启动接口加入鉴权中间件白名单，但路由必须验证 `launchCode`。接口按IP和启动凭证限频，生产环境要求Redis可用；Redis或限频状态无法确认时返回503，不继续创建场次。

### 7.2 Demo令牌

场次创建成功后签发JWT：

- `type`: `demo_merchant`
- `tenant_id`: 只允许等于 `DEMO_TENANT_ID`
- `dining_session_id`: 本次真实桌台会话
- `table_no`: 本次分配桌号
- `scope`: `demo_order_fulfillment`
- `exp`: 签发后30分钟

Demo令牌不包含owner角色，不复用正式merchant权限，也不写入正式登录存储。

### 7.3 中间件边界

鉴权中间件识别 `demo_merchant` 后只允许 `/api/v1/demo/*`。Demo令牌请求任何其它 `/api/v1/*` 路径必须返回403。正式merchant、member和staff令牌的原有处理顺序与行为保持不变。

Demo路由只从 `request.state` 读取鉴权结果，不自行解析Authorization头。

### 7.4 数据隔离

每次查询和更新必须同时带：

- `tenant_id == DEMO_TENANT_ID`
- `dining_session_id == token.dining_session_id`
- `order_id` 属于同一租户和同一桌台会话

只按 `order_id` 查询后直接操作属于禁止实现。需要为跨场次访问、跨租户访问和过期令牌编写行为测试。

## 8. API设计

所有接口沿用仓库权威响应 `RespVo { code, msg, data }`，使用 `success_response` 和 `error_response`。现有接口不改字段。

### 8.1 创建演示场次

`POST /api/v1/demo/sessions/start`

请求：

```json
{
  "launchCode": "体验卡启动凭证"
}
```

成功数据：

```json
{
  "demoToken": "30分钟JWT",
  "expiresAt": "ISO-8601时间",
  "diningSessionId": "桌台会话标识",
  "tableNo": "DEMO-01",
  "customerCodeImageUrl": "/static/entrance-codes/{scene}.png",
  "shopName": "开心点单体验店"
}
```

失败：启动凭证无效返回403；限频或桌位池已满返回429；系统无法确认分配结果返回503。

### 8.2 获取本场次订单

`GET /api/v1/demo/session`

请求头携带Demo令牌。返回场次剩余时间、桌号、订单列表和场次状态。订单字段只保留本次履约需要的订单号、菜品、数量、备注、创建时间、订单状态和上菜状态，不返回顾客手机号、会员资料、支付凭证或其它个人信息。

### 8.3 更新订单状态

`PATCH /api/v1/demo/orders/{orderId}/status`

请求：

```json
{
  "status": "preparing"
}
```

仅允许现有状态机中的 `pending -> preparing -> done`。后端调用现有订单生命周期服务，不复制状态机。重复提交保持幂等；越级操作返回409；不属于本场次的订单返回404，避免泄露其它场次是否存在。

### 8.4 确认上菜

`POST /api/v1/demo/orders/{orderId}/serve`

只允许本场次已经制作完成且尚未上菜的订单，复用现有上菜服务。重复请求保持幂等。

## 9. 商家Demo工作台

新增 `admin-h5/src/views/DemoWorkbench.vue`，不复用正式商家Layout和登录态。

页面结构：

1. Page Header：开心点单双端体验、30分钟倒计时。
2. 准备区：场次创建中的loading、失败原因和重试动作。
3. 顾客点餐区：大尺寸小程序码、桌号、三步提示。
4. 主任务区：本场次订单列表，新订单置顶并突出“待接单”。
5. 操作区：每张订单只显示当前合法的一个主要动作。
6. 反馈区：同步中、同步失败、操作成功、操作失败和场次过期分别展示。

状态必须区分 `loading`、`empty`、`error`、`success`、`unknown`：

- `empty` 只能表示场次已创建且尚无订单，文案提示“请用另一台手机扫描上方顾客点餐码”。
- 网络失败不能显示成“暂无订单”，保留上一次可信订单并标记可能过期。
- 状态操作未被后端确认前不能提前展示成功状态。
- 场次过期后禁用所有操作，并提供“重新开始30分钟体验”。

移动端优先。新交互使用Ant Design Vue，不引入新依赖，不复制现有完整订单管理页。

## 10. 顾客端行为

顾客码仍进入现有 `pages/entry/index`，解析演示租户的 `EntranceCode`，建立真实桌台会话并进入菜单。演示桌码使用 `channel=DEMO`，小程序只针对该渠道做两项最小行为：清除既有顾客登录态，并直接走匿名提交，不展示加入会员选项。

演示租户使用后付模式，因此提交订单不唤起微信支付。后端会员登录入口同时拒绝 `DEMO_TENANT_ID`，防止绕过前端向演示租户提交手机号或建立会员。顾客端的订单状态轮询继续按现有逻辑展示商家处理结果。

除 `channel=DEMO` 的匿名提交分支外，不改变小程序正式门店的入口、会员、结算和订单状态逻辑。

## 11. 数据生命周期

- Demo令牌30分钟后自然失效。
- Demo工作台只显示令牌对应的 `DiningSession`。
- 分配新场次前，后端将超过30分钟的演示开放会话标记为过期。
- 演示订单保留在专用演示租户中用于问题排查，但不进入真实商户统计。
- 后续若数据量达到运维阈值，再增加独立清理任务；第一阶段不增加定时任务或删除逻辑。

## 12. 错误处理

- 启动凭证错误：显示“体验入口无效，请联系工作人员更换体验卡”。
- 桌位池已满：显示“当前体验人数较多，请稍后重试”。
- 顾客码缺失或失效：场次创建失败，不展示无法扫码的占位图。
- 订单轮询失败：保留上次可信订单，展示“订单可能不是最新”，提供重试。
- 状态操作冲突：重新拉取本场次订单，展示后端确认的当前状态。
- 场次过期：清除 `sessionStorage` 中Demo令牌，禁止继续操作。

## 13. 测试与验收

### 13.1 后端

- 有效启动凭证创建30分钟场次并分配唯一桌位。
- 并发启动不会分配同一张桌。
- 桌位池满时失败，不复用活跃会话。
- Demo令牌只能访问Demo路由。
- 过期、伪造和错误scope令牌失败关闭。
- 跨租户、跨场次和跨订单访问全部失败。
- 订单列表不包含手机号、openid、支付交易号或会员资料。
- 合法状态迁移和上菜成功；非法迁移、退款、结账、打印与配置操作不可达。
- 运行租户隔离扫描和相关订单生命周期测试。

### 13.2 商家后台

- `/demo` 无需正式商家登录即可进入。
- Demo令牌只写入 `sessionStorage`，不覆盖正式token和tenant信息。
- loading、empty、error、success、unknown和expired状态可验证。
- 新订单轮询出现，按钮随状态只展示一个合法主动作。
- 状态更新失败不保留成功外观。
- Vue SFC解析、脚本编译、模板编译、相关单测和生产构建通过。

### 13.3 端到端验收

1. 老板手机打开Demo工作台。
2. 第二台手机扫描页面顾客码。
3. 顾客端选菜并提交，不发生微信扣款。
4. 订单在2秒内出现在老板手机。
5. 老板完成接单、制作完成、确认上菜。
6. 顾客端看到对应状态变化。
7. 用另一场Demo令牌无法看到或操作本场订单。
8. 30分钟后原令牌无法继续请求。
