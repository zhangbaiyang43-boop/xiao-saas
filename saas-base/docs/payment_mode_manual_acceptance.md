# 三种收款模式手工验收清单

## 前置检查

- 后端已执行数据库迁移：`py -3.10 -m alembic current` 显示当前版本为最新 head。
- 商家后台微信支付页显示“已验证”，收款账户已锁定。
- 小程序重新编译，启动页使用 `subpkg-order/pages/menu`，启动参数带真实 `shopId` 和 `table`。
- 测试桌台建议使用空桌或先完成/关闭历史会话，避免旧订单干扰。

## 先付后厨 `prepay`

1. 后台选择“先付后厨”，点击保存，刷新后仍选中该模式。
2. 小程序进入点餐页，下单确认弹窗应显示微信支付语义。
3. 点击提交后必须先生成订单，再发起微信支付。
4. 未支付或取消支付后，商家后台不应把订单当成可制作订单处理。
5. 支付成功后订单进入 `pending`，商家可接单，打印允许自动触发。
6. 重复微信支付回调或重复查询订单，不应重复发券、重复积分、重复打印。
7. 出餐完成（`done`）后，商家在桌台视图点"结账"，订单应能正常推进到 `settled`（先付后厨的订单
   这时候 `payment_status` 早就是 `paid`，结账动作不应该、也不会再改一次支付状态或支付方式，
   只是把订单标记为已完成、生成顾客端"消费记录"）。
8. 结账前如果这一桌先付后厨的订单一直卡在 `done`，说明结账逻辑又把它们漏结了——这桌会变成
   商家后台清不掉的"幽灵桌台"，点结账要么没反应、要么在会话已关闭后报"本桌没有进行中的会话"。

## 餐后付款 `postpay`

1. 后台选择“餐后付款”，点击保存，刷新后仍选中该模式。
2. 小程序点餐提交后不应弹出微信支付。
3. 订单创建后应进入 `pending`，`payment_status` 保持 `unpaid`。
4. 商家后台可接单、备餐、完成。
5. 商家把订单流转到 `settled` 时，后端应把订单标记为 `paid`，`payment_method=offline`。
6. 未结账前不可打印收据；厨房单可按订单创建/补打规则打印。

## 桌台账单 `table_account`

1. 后台选择”桌台账单”，点击保存，刷新后仍选中该模式。
2. 同桌多次点餐均不应弹微信支付，每笔订单进入 `pending` 且 `payment_status=unpaid`。
3. 有 `pending` 或 `preparing` 订单时点击桌台结账，应提示”本桌还有未完成的订单，无法结账”。
4. 只有所有需要结账的订单都到 `done` 后，桌台结账才允许执行。
5. 结账只应处理 `done + unpaid` 的订单；已取消、已拒单、已结账订单不能重复计入金额。
6. 结账成功后会话关闭，`active_key` 释放，同桌可重新开新会话。
7. 连续点击桌台结账或多人同时结账，不应重复收费或重复标记金额。
8. 小程序”已点菜品”里的”吃好了，去结账”按钮，只有本桌所有有效订单都到 `done` 才可点；
   还在 `pending`/`preparing` 时应显示禁用态”制作中，暂不能结账”，不能像过去那样点了以后
   被后端 `settle-table` 拒绝。
9. 点击”吃好了，去结账”后应调用 `POST /v1/dining-sessions/checkout-request`，把
   `dining_sessions.checkout_requested_at` 记下来；按钮变为禁用态”已呼叫服务员，等待确认”，
   刷新页面后这个状态应该保持（不是纯前端临时提示）。
10. 商家后台桌台视图对应这一桌应显示”顾客催结账 ⏰”，结账按钮文案带上”顾客催结账 · “前缀；
    商家点了”继续加菜”（顾客侧）以后再下单，这个催结账状态应该自动清除，不能一直挂着旧请求。

## 异常回归

- 历史订单“再来一单”必须按当前菜单重新校验：下架、售罄、规格变化不能直接加入购物车。
- 未登录客户可以基础点餐；只有查看会员资产或使用会员能力时才触发登录。
- 切换收款模式后，小程序应重新进入页面或重新加载店铺信息，避免使用旧模式缓存。
- 真机调试时如果看到仍然要求微信支付，先确认后台保存成功、接口 `shop_info.payment_mode` 返回值、小程序是否重新编译。

## 按桌码分区路由（新增）

1. 商家后台"桌码管理"新建一张桌贴码，桌号填 `Q1`，桌台分区选"简餐区"；再新建一张桌号 `F1`，分区选"正餐区"；再新建一张桌号 `N1`，分区留空（跟随店铺默认）。
2. 把店铺整体收款模式（PaymentSettings 页）改成和分区不一样的模式，比如整店选"餐后付款"。
3. 扫 `Q1` 桌码下单：小程序应走微信支付语义，返回的 `payment_mode` 应为 `prepay`，不受店铺整体"餐后付款"设置影响。
4. 扫 `F1` 桌码下单：应走桌台账单流程（不弹微信支付、多次加菜共用一本账），返回的 `payment_mode` 应为 `table_account`。
5. 扫 `N1` 桌码或不扫码直接柜台下单：行为应该和改动前完全一样，跟随店铺整体设置（这里是"餐后付款"）。
6. 桌码列表页应该能看到每张码当前的分区标签（简餐区/正餐区/默认分区），确认后台配置和实际路由结果一致。

## 通过标准

- 三种模式均能从“后台保存 -> 小程序下单 -> 商家处理 -> 支付/结账状态落库”走通。
- 预付只走微信支付；餐后付款和桌台账单不调用微信支付下单接口。
- 所有订单状态和支付状态可解释、可恢复、不可重复结算。
